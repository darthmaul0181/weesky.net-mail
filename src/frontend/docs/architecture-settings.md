### The settings module

**Settings module** — `SettingsLayout` (`src/modules/settings/SettingsLayout.tsx`) renders a `.context-pane` of `NavLink`s (Account / General / Connected accounts / Appearance / Folders / Aliases / Identities / Rules / Administration — Account, Aliases and Administration shown only for the primary account, Administration additionally requiring `isAdmin`, Rules requiring the primary account or a Sieve-capable domain) beside a `.settings-content` `<Outlet/>`. **Each row carries the icon its own page's title carries** — `UserIcon`, `SlidersIcon`, `PersonPlusIcon`, `DropletIcon`, `FolderIcon`, `AtSignIcon`, `MailIcon`, `FunnelIcon`, `ShieldIcon` — which is the site's trigger/title continuity rule, not a free choice: changing one without the other is the drift the rule exists to prevent. The icon takes `currentColor`, so the active row's foreground carries it, and `flex: none` keeps it from shrinking to buy the label a few pixels. **The 200px column leaves 134px of text once the icon and its gap are taken, and that number was read off a browser rather than computed.** Four things spend the other 66 — the pane's `border-right` and its padding, the row's own padding, the icon, and the gap between the icon and the label — and the arithmetic is easy to get wrong in the roomy direction: a previous note here claimed 155, having dropped both the row's padding and the border, and read the nav as having 24% of headroom. Re-measure it (`probes/localisation-widths.html`, below) rather than re-deriving it. The widest label the tree can draw is English `Connected accounts` at **128px** in the active row's 600 weight (125.4 at 400, which is where the old note's "125" came from) — **six pixels of headroom, not thirty**. French is the shorter of the two languages here: `Comptes connectés` spends 124px active, `Administration` is byte-identical in both, and nothing else clears 70. So the nav fits English and French and has almost nothing left for a third: a label past 134px wraps, and **the fix is the column width rather than the icons** — the icon/title continuity rule above is load-bearing and 200 is not. Module directories under `src/modules/settings/`:
- `general/` — `GeneralPage.tsx`, grouped under four `.account-section` headings rather than run as one list: **Layout** (reading pane, messages per page, message-list preview, the quick-action picker), **Privacy & security** (always-show-remote-images with always-show-images-from-contacts nested under it, spam-score visibility), **Composing** (default editor, then save-new-recipients; the heading is where a signature and a reply-quoting rule will land), **Notifications** (new-mail sound, desktop notification, plus the three mutually exclusive permission notes, which stay conditional because they are state rather than description). The headings are Appearance's, so the two settings pages group alike instead of in two dialects. **The quick-action picker is toggle chips (`.action-chips`), deliberately not the `.layout-card` skin the reading pane uses two rows above it**: one control taking several answers drawn exactly like one taking a single answer is separated from it by a 12px box against a 12px disc. The chip is a `<button aria-pressed>` — the `--action-primary` fill *is* the state, so there is no box to tick, and `aria-pressed` is what carries that to anything not looking at the colour

**The default editor is `mail.composeFormat` (`html`|`text`, default `html`) and it governs every composer but a resumed draft** — new, reply, reply-all, forward and edit-as-new all take it, because answering a mailing list is the case plain text exists for and it is the one `composeSeed.ts` used to force into HTML by writing `text: null` literally three times. `applyComposeFormat` (`compose/composeSeed.ts`) is where it is applied, once, in a `useMemo` with an empty dependency list so changing the setting never reformats a message being written. **Its carve-out tests `seed.action === 'draft'`, never `seed.text`**: an HTML draft carries `text: null` exactly like a reply, so a body test cannot tell them apart and would throw the draft's body away — the same boundary `ComposeView` draws for its dirty flag. Clearing each attachment's `contentId` is the whole of the inline-image handling, since the composer already splits the seed's attachments on that field. A `mailto:` needs no case of its own: `mailtoSeed` declares itself `editAsNew`. **`ComposeView` renders `LoadingBlock` until preferences arrive**, which nothing else in that file needed — `captureRecipientsOf` is read at send time, this is read at mount, and without the gate the composer opens in HTML and flips to a textarea under whoever has started typing. That gate is also why `ComposeView.test.tsx` primes the query cache from a module-level `prefs` rather than letting the api mock resolve asynchronously: 84 tests queried the DOM against the spinner otherwise. The preference path never reaches the `losesFormatting` confirm dialog — the choice was already made in Settings, and asking again on every reply is noise
- `account/` — `AccountPage.tsx` (identity, other domains, quota via `QuotaBlock`, `ChangePasswordSection.tsx`)
- `appearance/` — `AppearancePage.tsx` (theme + palette radio groups, backed by `ThemeContext`). Each palette card carries a thumbnail that **declares the palette it advertises** rather than the active one, and a hover-revealed loupe opening the same preview enlarged, in **both** modes at once — the thumbnail can only ever show the mode in use, and a palette is picked once for both. Two things are load-bearing: the loupe sits **outside** the card's `<label>`, since inside one a click on it activates the label's radio and asking to look at a palette would apply it; and the preview's every length is a multiple of one `--pp` scale, so `.is-large` changes that number alone and the two sizes cannot drift. The preview shows the compose button and the attachment chip because both carry `--action-primary` — without them twelve palettes read as twelve greys
- `mail/` — `FoldersPage.tsx` (everything about folders in one place: the full list via `FolderManager`, plus the two dialogs that act across the whole set) and `SystemFoldersModal.tsx` (system role assignment; the `<select>`s exclude the inbox, non-selectable folders, and folders already overridden for another role)
- `aliases/` — `AliasesPage.jsx` (slimmed to alias CRUD only; the old `AccountPanel` slide-in was retired in favor of `AccountPage`)
- `identities/` — `IdentitiesPage.tsx` (the curated From list, styled as Administration tiles: each tile is `<display name> — <alias>` with a star to set the default, an edit button and a delete, sorted alphabetically by display name; the primary carries a `primary` tag and neither edit nor delete — its name is the live account FullName, patched in from `useAuth().identity` so an Account-tab change shows at once — and a stale identity carries an `unavailable` tag and a delete only) and `IdentityDialog.tsx` (the add/edit modal in the admin shape — `.field-h` rows, one `.btn-primary`, the ✕ as the only way out; the alias field is a type-to-filter combobox like the virtual-domain owner picker over `useAliases()`, fixed once an existing identity is being edited). Every action `PUT`s the whole set — there is no per-row endpoint — so `IdentitiesPage` keeps an `edited` list of its own between actions: each mutation has to build on what the one before it produced, since the invalidation's refetch has not necessarily landed yet, and it is dropped the moment fresh server data arrives or a save is refused, so a refusal always leaves the page showing server state rather than an optimistic lie. **The page is keyed on the active account** (the default export is a one-line wrapper around `IdentitiesPanel`): a replace in flight blocks that drop, so without the key an optimistic list built from one mailbox survived a switch and the next star or delete PUT it over the other mailbox's set
- `rules/` — `RulesPage.jsx` (Sieve rules manager, unchanged wizard/provider logic — see below)
- `admin/` — `AdminPage.jsx` (tab bar: Accounts / Domains / Virtual domains) with `AccountsTab.jsx`, `DomainsTab.jsx`, `VirtualDomainsTab.jsx` (**not** `OwnershipTab` — renamed to match the `domains/virtuals` API and "virtual alias domain" terminology), `AddEditUserModal.jsx`, `AddEditDomainModal.jsx`

**The circular logo ships at 192px and 32px, never at source size.** `logo_circle.jpg` was a 3808×3854 PNG misnamed `.jpg` — 541 KB downloaded on every first load to be drawn at 26px in the topbar. `logo-192.png` (8.5 KB) serves the topbar, the apple-touch icon and the desktop notification's `icon`; `favicon-32.png` (853 B) is the tab icon. Both were box-filtered down from the original with alpha premultiplied, so the transparent edge does not bleed dark. If the logo is ever replaced, regenerate both rather than pointing a `<link>` at whatever the designer exported.
`RulesPage.jsx` key components: `RuleCard`, `RuleEditorModal` (step wizard: name → conditions → actions → options), `ConditionRow`/`ActionRow`, `ConvertConfirmModal`. The **Extended rules** toggle switches provider: ON = Weesky (native, full feature set), OFF = Rainloop (Snappymail-interop, restricted) — turning OFF runs `api.checkCompatibility` first and shows `ConvertConfirmModal` for rules that would be dropped. See the repo-root `DESIGN-rules.md`.
