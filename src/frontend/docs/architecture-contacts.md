### The contacts module

**Contacts module** — `ContactsLayout` (`src/modules/contacts/ContactsLayout.tsx`) builds three columns inside the shell's single outlet, the way `MailLayout` and `SettingsLayout` do: the scope band, `.contacts-list` and `.contacts-card`, with the mail module's `PaneSplitter`/`usePaneSize` between the last two under a key of its own (`contacts.split.right`, 380 default / 240 floor) — per-device localStorage for the same reason the mail splitter's sizes are. `/contacts/new` and `/contacts/:id/edit` are two further routes pointed at the **same** lazy layout, not layouts of their own: `useMatch` swaps the list and the card for `ContactEditView` while the band stays put, exactly the `/mail/compose` mechanism, so a scope is one click away without leaving the form. **A contact id travels in a route segment where a folder path never could** — it is a GUID, so none of the separator trouble applies — but the *selected* contact stays in a search param (`?id=`), because opening a card is a selection while opening the editor is a different surface. Choosing a scope drops the selected id, for the reason choosing a folder drops the uid: a contact filtered out of the new scope must not stay open. Deleting goes through the shared `DeleteConfirmModal`, the module's only dialog.

**The band exists for what lands in it, not for its two rows.** `ContactScopes` carries All contacts and Favourites with their counts and nothing else; `ContactsTransfer` is a single trigger in the column's **top** row, beside Add contact, opening a menu onto `Import…` and `Export` — file actions rather than navigation, which is why they are not rows among the scopes. **The column has no footer at all**, and losing it is the point: the two were filled `.btn` boxes across its foot, the heaviest pair in the column after its primary action, for its two rarest actions, in a shape nothing else in the app wears. What replaced it is `.column-actions`, the row the mail folder column opens with — shared rather than transcribed, the two copies having drifted 4px wide and 2px tall apart — a primary action on `flex: 1` and one 40px square beside it, and the trigger costs that button 47px: `+ Ajouter un contact` measures 131.9px of ink against the 141 left, English 90.8, so a third language or a reworded label is a re-measurement in `probes/localisation-widths.html` rather than a judgement call. **Below 1024px the trigger moves into the list's own selection band**, because the stylesheet hides that top row inside the drawer — Add contact is the floating button there — and a file action left in a hidden row is a file action deleted. That is the road `Refresh` takes out of the mail's folder column, and `ContactsLayout` renders exactly one instance on either side of the `inDrawer` test: the component owns the hidden file input and the import report, and a second copy behind a media query would be a second modal nobody closed. The one reachability gap left is the editor route under a drawer, where no list band is mounted; importing while filling a form is not a gesture, and the desktop keeps the trigger there. The band wears the navigation language (fill plus weight, `aria-current` on the active row like `FolderTree`) and **no accent bar**: the bar belongs to content lists, and the selected tile is what carries it. **The import goes straight through**: the file posts on pick, the server merges on the address and answers a report, and `ImportReportModal` prints the four counters plus every refused line with its number — there is no preview step, because the merge overwrites nothing and replaying a file creates nothing. Its mutation invalidates `onSettled` like the module's four others, so a refused import still resyncs the book. **The hidden input is cleared before the upload is awaited**: an input that keeps its value fires no change event when the same file is picked twice. `Export` is disabled on an empty book — a file with no rows reads as a failure — and downloads through the shared `lib/downloadBlob.ts`, extracted from `MessageReader` so the two cannot drift. Its refusal used to be a tooltip on a button and is now the menu row's `title`, which is what forced `shell.css` to grow a `.dropdown-item:disabled` rule at last: there was none, so every disabled menu row in the app — the reader kebab's Delete with no trash folder included — was drawn exactly like a live one.

**`contactName.ts` and `contactSearch.ts` are the module's whole shared surface** — everything else in the folder is a screen. `displayNameOf` is the one place a contact is named (first + last, else nickname, else the first address): the tile, the card, the editor's heading and the composer's dropdown all call it, because four screens naming one contact four ways is the defect it exists to prevent. `primaryAddressOf` is `addresses[0]` and nothing more, since position 0 *is* the primary — the backend stores an order, never a flag, so there is nothing that could fall out of step with it. `fold`/`matches` strip diacritics with `\p{M}` and lower-case, the same normalisation `folderFilter.ts` performs and for the same reason (nobody reaches for the é key to look somebody up); the page's filter and the composer's dropdown call the identical predicate, so the two can never disagree about what "matching" means.

**One address may belong to several contacts, and that is what shapes the autocomplete.** Nothing at any layer forbids it — a household or a shared mailbox is a real contact each — so `suggestionsFor` keys its rows on the **folded, trimmed address** rather than on the contact: one address is one row carrying every name that holds it, because two rows inserting the identical recipient are indistinguishable from a bug. Only the key is canonical; the row still displays the address as stored, so the spelling on screen stays the user's own. Rows sort favourites first, then a primary address ahead of a secondary one, then alphabetically, and cap at ten.

**The composer's field highlights nothing until an arrow says so.** `RecipientsField`'s `active` starts at `-1` and returns there on every keystroke: Enter must commit what the user typed, never substitute a suggestion they never looked at. Escape hides the list without discarding the query, so an arrow brings it back and lands on the end it came from. The `<ul>` preventDefaults its own `mousedown` **on the container**, not per row — a mousedown on the scrollbar or the padding strip blurs the input, and blur commits the half-typed draft as an invalid token. `ComposeView` calls `useContacts()` once and hands the array to all three fields; the prop defaults to `[]`, so an account with no contacts keeps the field's pre-suggestion behaviour exactly.

**The card's three actions take the tile's arrangement above 640px and the reader's band below it, and neither is a bottom row of buttons any more.** They used to be three `.btn` boxes in a band under the card: in French they come to ~440px against the 272 a 360px screen leaves once the 88px reserved for the floating add button are taken, so the row wrapped onto two lines, and the gap beside the first line was not whitespace but a corner held for a button nothing on screen explained. From 640px up the cluster is in the head beside the name — `.contact-star` then two `.admin-icon-btn`, the tile's own vocabulary rather than a third dialect, with the star **outside** the cluster because it is a flag and not an action, exactly where the tile puts it, and Delete one click deeper in a `DropdownMenu`. Below 640px it is `.actionbar`, the shared band `shell.css` declares and `MessageReader` draws the same way: three named cells, `Favori` / `Modifier` / `Supprimer`, 56px each in a 57px band, measured in `probes/mobile-layout.html`'s `contact action bar-360`/`-320`. Four things about it. **`bottomActions` is a prop, never a `useViewport()` of the card's own** — `MessageReader`'s reason exactly: the layout is what knows the tier, and deriving it twice is how the two fall out of step. **The band spends no cell on a kebab**: the card holds three actions, and a last cell that could only ever open a one-entry menu would spend a third of the screen saying nothing — which is also why Delete is a full cell here and a menu row up there, the one place the two shapes deliberately disagree. **`AppShell` withholds `BottomNav` while the card is open**, on `?id=` the way it does on `?uid=`, so the 57px are repurposed rather than doubled; on a phone the card has replaced the list, so the Contacts tab would point at where the user already is and the ← is the real way out. And **`ContactsLayout` drops the floating add** under the same condition, since it is anchored 73px up from the edge the band now owns — `MailLayout` drops the compose button for the identical collision. The cluster's own touch floor lives in `@media (hover: none)` rather than the phone block: 28px and 22px boxes need 44 on a **touch tablet**, which is the one tier where `--touch` is not declared at all and the one tier that draws the cluster on a finger.

**One tile skin, on two lines** — star + name + actions, then the address underneath. The message list carries two skins because three pane arrangements exist there; here the list always sits beside the card, so a wide skin would be code nothing can reach. The address line renders even when empty, so an address-less contact is not a shorter tile than its neighbours, and it carries `· +N` when the contact holds more than one.

**The editor waits for the book *and the card* before it mounts, and an unknown id is not an invitation to create.** `ContactEditView` seeds its state from its contact once, at mount, so mounting it on an edit route before `useContacts()` has answered would seed an empty form that the arriving data would never reseed — `ContactsLayout` holds the loading/error line until the book is in hand. It edits a `ContactDetail`, not the list row: the row carries neither the line positions nor the display name, so an editor mounted before `useContact()` answers would seed without them and every save would rebuild the card's `EMAIL` block and recompute its `FN`. The same reason, therefore the same gate — in create mode there is no card and nothing changes. Once it *is* in hand, a route id the book does not resolve is a target that no longer exists (an obsolete bookmark), so the layout toasts and redirects to `/contacts` with `replace`; it used to fall through to create mode, where saving fabricated a second contact. The search-param variant (`?id=unknown`) instead keeps the "select a contact" invite, the way mail treats a vanished message. The editor is keyed on the contact being edited so switching from one edit to another reseeds it, and `saveError` is cleared when that key changes — otherwise a refusal on one contact sits above the next contact's form.

**The list selects like the message list, and its heading is that module's band.** `ContactList` draws `SelectionBand` (`src/components/SelectionBand.tsx`) with its search field and total in the centre slot, and one action beside them: delete the selection. Each tile carries a checkbox in the 34px gutter `.contact-tile`'s left padding reserves permanently — revealed on hover or focus, pinned once anything is checked, exactly as `.message-row-check` behaves — and clicking it stops the event rather than opening the card. **The reset key is scope + query**, so leaving the scope or typing a letter empties the selection: the owner's call, against the initial recommendation, and the price of the two modules behaving identically. **Typing is not actually reachable while a selection stands**, because the field is what the count replaces; the band therefore grows a **loupe** in that state, and using it clears the selection and puts the caret back in the field. That is the one place the two modules only half resemble each other, and deliberately: the mail searches one folder among fifteen and gains by asking for its bar, the book is a single list where searching is the common gesture, so its field is permanent at rest. **`useSelection` is imported from `modules/mail/list/`** rather than moved to `src/hooks/` — it is generic on the key (`useSelection<string>`, the GUIDs) and the mail is its other caller, so the two would have to move together. A deliberate deferral, not an oversight; `buildDragPill` is imported across the same seam, parameterised on its label and glyph rather than copied.

**Deleting a selection is one call, behind the shared confirm.** `onDeleteMany` reaches `useDeleteContacts` → `DELETE /api/Contacts` with the ids in the body, capped at 200 server-side, an unknown id being a silent no-op: a batch may not half-fail, and fifty contacts would otherwise be fifty requests with nothing to say about a failure at the thirtieth. The dialog is `DeleteConfirmModal` with a pluralised message; the list clears its own boxes on confirm, and a refusal toasts and leaves the screen on server state, since the mutation invalidates `onSettled` like every other one here.

**Dragging tiles onto a scope adds the favourite and never removes it** (`contacts/dragContacts.ts`). A drag carries the whole checked selection when the grabbed tile belongs to it and that tile alone otherwise, under a MIME of its own (`application/x-weesky-contacts`) so a message dragged over the column offers nothing. `canDropIntoScope` refuses `all` — the complete view, not a group — which is the refusal `canDropInto` makes for the mail's source folder, and groups will be targets by construction when they land. A gesture that added *or removed* depending on each row's state would land a different result per contact, which is why the drop only ever sets the flag. Each `ScopeRow` holds its own `drop-ready` state, since one flag on the band would light every row at once, and passes its `--drop-label` from the catalogue — the fix that also took the hard-coded English `Drop here` out of `mail.css`.

**The card reads `GET /api/Contacts/{id}`; the list carries only what a tile shows.** `useContact` is called by `ContactCard` itself — the precedent is `MessageReader`, which fetches its message rather than being handed one — and the card paints immediately from the list row it already receives, then enriches: the name and the addresses are there before the detail is, or every selection would begin with a blank. The addresses come from the detail once it has landed (the server ranked them by `pref` then `position`, so no screen re-sorts them) and from the list until then. The `detail` and `photo` keys sit under `contactKeys.all`, so the invalidation every write already fires refreshes the open card without a line of its own. **The picture goes through `requestBlob`, never through an API URL in a `src`**: it sits behind the session cookie on another origin, which an `<img>` element does not send — the reason the reader's attachment images take the same road. The object URL is revoked with the blob that produced it, or every contact opened would leave its picture in memory for the life of the tab.

**`formatBirthday` (`contactBirthday.ts`) never invents a year.** A vCard allows `--0315`, and that is the common case for a contact who never volunteered one; formatting it as 1900 would state what the card does not say. The three forms a phone exports (`19930621T115900Z`, `19930621`, `1993-06-21`) are read, and everything else is shown as the card wrote it: a birthday that disappears reads as data lost, where an odd-looking one reads as a card to correct.

`contacts/queries.ts` — `useContacts()` on `['contacts', accountId]`, scoped by account from the outset like the mail keys, with a 5-minute `staleTime` since only this module writes to it, and sorted in `select` so the page and the composer read one already-ordered list instead of each sorting its own copy. Every mutation invalidates **`onSettled`, not `onSuccess`**: a refused write must leave the screen on server state rather than on an optimistic lie.

**`useAccountId` lives in `src/hooks/`, not in `modules/mail/queries.ts`.** Contacts key their cache on the account too, and a module reaching into another module's data layer for the account identity is a coupling nothing justifies; it moved with all seven of its importers.
