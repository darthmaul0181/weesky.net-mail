### Routing, guards and the shell

**Routing** — `react-router` v7, `createBrowserRouter` defined in `src/routes.tsx` (the route table lives there). `MailLayout`, `ContactsLayout`, `AliasesPage`, `RulesPage`, and `AdminPage` are `lazy()`-imported in `routes.tsx` and wrapped in `<Suspense fallback={null}>` at the route level, so the shell/settings chrome never waits on their bundle. The root route is pathless and carries no `element`, only `errorElement: <RouteError />`: a render-time throw anywhere in the tree — `/login` included — lands there instead of a blank tab, and a stale-chunk import (a tab left open across a deploy) reloads once on its own rather than showing the message at all. Offline, the same failed import does not reload — a reload would only reach the browser's own "no internet" page — and shows the offline message instead.

**Mail selection lives in search params, not route segments.** A folder path may contain `/` — the hierarchy separator is whatever the IMAP server uses — which is the same reason folder paths travel in the query string or request body on the API side rather than in a route segment. `/mail?folder=INBOX&uid=42` keeps deep links and the back button working under any separator. Choosing a folder drops `uid`, because a message id means nothing in another folder. **`MailLayout` opens the inbox when the URL names no folder** — found by the resolution chain's `inbox` role, not by matching the name, and written with `replace` so Back leaves the mail view instead of bouncing off the redirect. It never selects a message: that stays the user's call.

**`RequireAuth`** (`src/layouts/RequireAuth.tsx`) — reads `isLoggedIn` from `AuthContext`; redirects to `/login` if false, otherwise renders `<Outlet/>`. Everything except `/login` sits behind it.

**`RequireAdmin`** (`src/layouts/RequireAdmin.tsx`) — reads `isAdmin`/`accountLoaded` from `AuthContext`; renders nothing while the account is still loading (avoids a flash-redirect), then redirects non-admins to `/settings/account`.

**`RequireSieve`** (`src/layouts/RequireSieve.tsx`) reads `!== false` throughout, like `RequirePrimary`: `activeAccount` is null while the account list loads and the primary always carries `sieveSupported: true`, and an absent or still-loading `capabilities` reads as "available" rather than flash-redirecting. A connected account answers to its own `sieveSupported` alone, the primary additionally to `capabilities.rules`. **That second redirect waits on `accountsLoading`**: during the load a connected account's row has not landed, `activeAccount` is null and `isPrimary` reads it as the primary — right for a nav row, which re-renders when the list lands, wrong for a redirect, which bounced a Sieve-capable connected account deep-linking in while `capabilities.rules: false` answered first. Once the list is in, a genuine primary with `rules: false` still redirects.

**The session flush in `AuthContext` runs on the transition, never on a logged-out first mount** (the flush itself, and why it is `resetQueries`, is in CLAUDE.md's Auth section). On a first mount there is nothing cached to flush, and flushing anyway destroyed the in-flight queries of siblings mounted above the router — the app-settings read behind the install manifest among them, which left `/login` unable to offer installation. Knowing whether a session was running is `wasLoggedIn`, seeded from the session flag rather than a "first run" boolean, since StrictMode's second mount pass would spend that boolean on the mount itself. `sessionGeneration` is bumped on each ending, and `refreshAccount` checks it before every late `setState`, so a slow answer from an ended session cannot resurrect its account, `isAdmin` or capabilities.

**Shell layout** — `AppShell` (`src/layouts/AppShell.tsx`) renders `TopBar` + a body split into `AppRail` (left icon rail: Mail/Calendar/Contacts + a spacer + Settings gear, `NavLink`-driven active state) and `<main className="app-content"><Outlet/></main>`. `TopBar` (`src/layouts/TopBar.tsx`) carries the logo/wordmark and nothing else. **The account block is not in the topbar**: `IdentityMenu` (`src/layouts/IdentityMenu.tsx`) sits at the foot of the mail folder column, showing the initials pill, display name and email on the band itself, with a chevron opening a menu **upward** (outside mousedown and Escape close it) that lists every connected account and Sign out. **The menu is the account switcher**: a row calls `switchAccount`, the active one carries a tick, and one whose stored credentials no longer decrypt carries a chip naming its repair — `Password needed`, or `Sign-in needed` for an OAuth2 account — and refuses the click; the fix is on `/settings/accounts`, not here. On a connected account the band itself gains a second line naming the mailbox, so the column always says which mailbox is being read. It carries no Settings entry — the rail's gear is the single route there. Because it lives in the folder column, signing out is reachable from the mail module only; that is the accepted cost of putting the identity where the user reads.

**Mail module** — `MailLayout` (`src/modules/mail/MailLayout.tsx`) builds its own three columns inside the shell's single outlet, the same way `SettingsLayout` does: `.mail-folders` (folder tree plus management), `.mail-list`, `.mail-reader`. `/mail/compose` is a second route pointed at the same lazy `MailLayout`, not a layout of its own: `useMatch('/mail/compose')` swaps `.mail-list`/`.mail-reader` for `ComposeView`, itself `lazy()`-imported a second time so a plain reading session never downloads `squire-rte`.

**Every column is a band stack, not a scrolling box.** Each is `display: flex; flex-direction: column; overflow: hidden`, with exactly one band carrying `flex: 1; min-height: 0; overflow-y: auto` and the rest `flex: none`. That is what keeps the folder actions, the list heading, the pager and the attachment row on screen — all four used to sit at the end of their column's content and had to be scrolled to. **`min-height: 0` is the load-bearing part**: without it a flex child refuses to shrink below its content height, the scroll lands on the column instead of the band, and the pinned bands drift away again.

**Layers — Escape belongs to the topmost surface, Tab to the innermost trap.** `lib/layerStack.ts` holds one stack behind one `document` `keydown` listener, registered at module load so nothing the app installs later can get in front of it; `hooks/useLayer.ts` is how a surface joins it. Every dialog reaches it through `<Modal>`; `ContextDrawer` and the phone calendar editor call it directly. Menus (`DropdownMenu`), the toolbar's popovers and the calendar bubble join it through `hooks/useDismiss.ts`, which adds no trap and one outside-press listener. **A press outside answers to the traps above it, not to the top place**: a menu opened from a popover holds no trap, so one press on the page closes both, while a confirm a menu row opened does leave that menu standing underneath it. Escape goes to the topmost layer and calls its `onEscape` — which is what ends the drawer and a dialog closing on one key — while Tab cycles inside the innermost `trap` still standing, so a trapless layer over a dialog or the drawer (a menu, a popover) does not let the focus walk out of the surface it was opened from. **A layer with no `onEscape` still swallows it**, so nothing underneath reacts, and the swallowing is a `preventDefault()`: the contract runs both ways, the stack ignoring a keydown something nearer the target already prevented (a React `onKeyDown` goes first) and a handler outside the stack reading `defaultPrevented` before acting. A layer keeps its place for its whole active life, so a handler re-created by a render never jumps it above a newer one. **Order is push order, corrected once by containment.** React commits a child's layout effect before its parent's, so a surface drawn inside another pushes first — `pushLayer` therefore slips a layer whose container holds one already on the stack *under* it, and everything else lands on top. Nothing else is ordered by the DOM, which is why there is no portal: a portalled surface is drawn outside the markup that would say what it sits inside.

**Across a list or a grid, the keys are `hooks/useGridNav.ts`.** A `role="grid"` is one tab stop for the whole surface: the arrows walk the widgets its rows hold, Home and End the ends of a row, the same pair under `Control` the two corners of the grid, and the hook owns the roving `tabindex` so that no consumer ever computes one. Where that one stop opens is the state the consumer declares, in a fixed order — an explicit `aria-selected` or `aria-pressed` first, a contextual `aria-current` after it, the first widget when neither is there — because a dialog reopened on Coral must not hand Tab to Blue, and a month whose anchor is not today must not open on today. Four things a consumer renders rather than asks for. **Every focusable sits in a `role="gridcell"` of its own**: a cell holding two widgets is a cell the arrows cannot address, and the cell count per row must not move under a setting, or the shape the arrows walk moves with it. **A cell that is itself the activation target renders a constant `tabIndex={-1}`** — the mail row's content cell, the month's day cell — and never a value of its own computing, since the attribute is the hook's to move and a consumer writing it too fights the hook for it; a native widget inside a cell renders none at all, its own implicit `0` being exactly what the hook demotes. **The grid element has to exist at the hook owner's first layout effect**, the effect being keyed on the ref alone with nothing to re-run it when a conditionally drawn grid appears later: that is the whole reason `MessageGrid` and `ContactGrid` are components of their own, and why `MonthView`, whose own root is the grid, needs no such extraction. And **`focusablesIn` is not `tabbablesIn`** (`lib/layerStack.ts`, two views over one selector string and no third spelling anywhere): the first is everywhere focus can be *put*, a roving `-1` included, which is what the arrows walk; the second is where Tab actually goes, which a trap and a menu read. Reading the arrows' list where Tab's was meant is how focus walked out of a trapped dialog once — every widget a grid demotes is still in `focusablesIn`, so a trap built on it holds nothing.

**A widget the stylesheet hides at rest is revealed on `[tabindex="0"]`, through `:has()`, and never on `:focus-within` alone.** The hook arms the stop *before* it moves focus — it has to, since `.focus()` on a widget nothing draws is a silent no-op that would strand the walk on a dead key — so a rule waiting for focus reveals nothing and the grid becomes unreachable from the keyboard. The `focusout` net that recovers a stop the stylesheet has hidden reads `getClientRects()`, which is one layout read per departure and never one per mutation: it therefore sees a `display: none` widget (the mail row's cluster on a touch tier) and is blind to a `visibility: hidden` one (the contact tile's), where the reveal rule carries the whole weight on its own. **The matrix the arrows walk is rebuilt on `childList` and on `disabled`, and on nothing else** — one walk per mutation rather than one per keypress, an arrow having cost 19ms of walk at 2000 rows — so a consumer that changes what is reachable by any other means has to say so by moving a node or flipping a `disabled`. Cell entry **narrows that walk** rather than adding a `tabindex` of its own, and any future mode has to respect the same filter or widen it, not lay a second idea of the stops over it.

**What may sit in a cell, and what the grid will not spend.** A `<select>`, a radio group or a slider answers to the arrows itself, so it may only sit in a `cellEntry` grid, where the arrows walk the cells and **F2** is the way in. Header rows are walked like any other: nothing distinguishes a `role="row"` of column headers, so a sort button in one is row 0 of the walk rather than a band above it. `Shift`+arrow is reserved for a range selection this product has not built, so the hook answers no key carrying it. **Never redirect focus from a focus handler inside a grid**: `focusin` is how the stop follows a click, a caret leaving one cell for the next and the hook's own `.focus()`, and a consumer moving focus again from that same event fights a stop that has already moved. **And nothing reads `getComputedStyle` on the keypress path** — the hook's one layout read is the `focusout` net's. **A grid is not a layer**: its listener is the container's, not the document's, and it competes for nothing. Escape is spent only to leave an entered cell, and marked `preventDefault` when it is, so a swatch holding the focus in a grid with no `cellEntry` still closes the popover `useDismiss` registered under it, and a dialog underneath an entered cell does not close on the press that comes out of it.

**Inside one menu, the keys are `hooks/useRovingFocus.ts`.** It opens the surface on its first item (with `preventScroll`: that item sits against the trigger just pressed, and a scroll would close an upward menu, whose flip lands a frame later), walks it on ↓/↑ with a wrap at both ends, and sends Home/End to the two ends. ←/→ are left alone, since the menu pattern gives them to a submenu. It marks every key it spends `preventDefault` — which is what keeps the stack and the mail list's own row keys off the same keydown. **It moves real focus and rewrites no `tabindex`, and the list it walks is `tabbablesIn`** — the stack's own Tab order — so a menu standing over a trapped dialog cannot hold a second idea of where focus may go: the arrows are a subset of that dialog's Tab, never a set beside it, and a disabled row is in neither. Two bounds: the handler is the surface's own, so once focus has left it the arrows are the page's again; and a surface holding no focusable returns before marking anything, so the arrows fall through rather than being swallowed by an empty menu. Two consumers declare `role="menu"` and each is **named by its own trigger** through `aria-labelledby`, which is the only thing telling a reader landing on the first row which menu it is in: `DropdownMenu`, for every one of its seventeen call sites, and `IdentityMenu`. The Administration owner picker is the third, where the field and its matches are one surface — ↓ walks out of the box into the list, while **Home and End stay the caret's in any text box and ↓/↑ stay the caret's in a multi-line one**, which is the whole of what the walk yields. **The composer's two swatch grids are not consumers of it either**: eighteen colours in six columns are a grid, which the menu pattern cannot express — ←/→ are a submenu's there and Home/End name no corner — so they are `ColourGrid`s like the calendar's twelve (`components/ColourGrid.tsx`, drawn by `compose/SwatchGrid.tsx` and `calendar/ColorSwatches.tsx` — one body, one normalisation of the colour in force, one row-and-cell rule in `index.css` reading the `--swatch-size` and `--swatch-gap` each surface declares): three `role="row"`s of six `role="gridcell"`s, one tab stop for the eighteen, and the colour in force carrying `aria-pressed` so Tab lands on it rather than on the first swatch — which the highlight grid does, while the text grid seeds at `currentColor`, where nothing is in force and black is the honest landing. Each is still named by its own trigger through `aria-labelledby`, which is what spares eighteen swatches a catalogue key for the grid itself — they have one each for their names, since a reader hearing `#d0021b` learns nothing. **They opt out of `cellEntry`**, one widget per cell having nothing to enter, and that is what leaves Escape alone: the hook spends it only from inside an entered cell, so a swatch holding the focus still closes the popover `useDismiss` registered under it.
