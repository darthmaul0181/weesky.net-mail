# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`frontend` — a React SPA webmail for the weesky.net mail service (mail, calendar, contacts modules plus a settings area covering account, appearance, aliases, mail rules, and admin). It talks to a backend at `https://api.mail.weesky.net`. **Mail is built for reading**: folder tree with management, paginated message list, reading pane with attachments — a non-inline image attachment's chip splits into the plain download button plus a chevron opening a Download/View menu, the latter loading the image into a small modal viewer rather than a bare `<img src>`, since the API's session cookie would not follow a cross-origin image request — the two flags a reader actually sets — read/unread and star — and message actions — move, copy, archive, report as junk, and delete (a move to trash, or, inside trash, a confirmed permanent expunge). The list also supports **multi-select** (checkbox selection with a persistent bulk-action toolbar) and **emptying a folder** (purge trash/junk, or move everything out to another folder). **Composing** lives at `/mail/compose`, reached by the pencil, first among the selection toolbar's actions: it replaces the message list and reader while the rail and folder tree stay put, so a folder is always one click away without leaving the draft's screen. The body is a WYSIWYG HTML editor (Squire) behind a formatting toolbar; To/Cc/Bcc are token fields, with Cc and Bcc revealed on demand rather than shown by default. Attachments stage on pick — each file starts uploading the instant it is chosen, and the send request carries only the staged ids, never the file bytes. The whole compose surface, not just the attachment tray, is a drop target: dragging a file anywhere over it stages it, with a counter (not a boolean) tracking dragenter/dragleave so the overlay survives the pair firing at every child boundary. An image pasted onto, dropped on, or chosen from the toolbar's image button for the message body becomes an inline part rather than an attachment — `.compose-body` is the drop zone that tells the two apart from the surface around it, and the button is the keyboard and touch way in that paste and drop cannot be; all three land in `routeFiles`, the one place a file is sorted into body or tray — and is resized afterward with **Squire's own eight handles**, which write `style.width` plus `height: auto` onto the `<img>`; the size lives in the markup rather than in React state, so it survives a draft save and reopen (the outgoing sanitiser keeps the inline style, asserted in `OutgoingMailSanitizerTests`, and the resumed draft comes back through that same sanitiser). `insertImage` additionally writes `max-width: 100%`, the bound that stops an unresized full-size photo overrunning the recipient's column, and `.compose-editor` carries `position: relative` because Squire appends its handle container into that root and offsets it by the root's own `scrollTop`. **A bespoke three-width bar (Small/Best fit/Original) was built and removed; do not re-add it**: `squire-rte` constructs its `ImageResizer` unconditionally — there is no config flag — so a click on an image draws Squire's handles over any selection UI of ours, and appending them into the editor root is a DOM mutation Squire's own MutationObserver reports as an `input`, which closed the bar before it ever painted; dragging the native handles then wrote a `style.width` that beat the bar's `width` attribute anyway. That same spurious `input` still marks a resumed draft dirty on a bare click, a Minor left deliberately unfixed: the obvious guard — comparing `getHTML()` before forwarding `onChange` — must not be used, because `getHTML` detaches `.squire-image-resize-container` from the root to serialise the body and re-appending it drops the pointer capture a drag rides on, breaking the very resize it was meant to observe. The drop overlay's `pointer-events: none` is load-bearing: without it the overlay would sit between the cursor and `.compose-body`, covering the very target it announces and routing every image into the tray instead. Sending goes out over SMTP and best-effort files a copy in Sent; a failed copy still reports the send as sent. A "Save draft" button sits beside Send — below 640px it folds into a kebab there, along with the title, because the band carries no `flex-wrap` and its four items came to 462px of content in a 360px column: Save draft was cut off and the ✕, the only visible way out, ended a hundred pixels off screen. Two more phone rules answer the same budget, measured on the whole surface: **the formatting toolbar folds to one row behind a `⋯`** (`is-extra` on five of its nine groups, hidden by the stylesheet rather than unmounted so an open popover survives a fold — seven cells is what fits one row at 320 as well as 360, eight already wraps at 320), and **`AttachmentTray` renders nothing while no file is staged**, its Attach button having moved into that toolbar beside the image picker it shares a file dialog with. The composer's labels also go back BESIDE their controls against `index.css`'s phone rotation, which is right for a settings row's sentence-length captions and wrong for `De`, `À`, `Cc`, `Cci` and `Objet`. Together, measured at 360 and at 320: the body goes from 102px to 347, 16% of the screen to 54%. **That number is the keyboard-closed one, and the keyboard is the whole point**: measured on a Galaxy S25, the software keyboard takes 426px of an 832px screen, so the composer only ever has 406 while anything is being typed and the body was back to 113px — four lines, what it had before any of this. So below 640px **the fields fold to a one-line summary once the caret enters the body**, and the body goes to 214 (`compose-keyboard-384` / `-folded` in the probe). Four things about it. The trigger is the **body's focus**, never the keyboard, which opens on To and on the subject too and would fold the fields at the very moment they are being filled. The fields are **unmounted, not hidden** — hidden they would keep their place in the tab order — and nothing is lost, since the caret reaching the body has already blurred the recipients field and committed its half-typed token. The summary **names the recipients through `namesByAddressOf`**, exported from `RecipientsField` for exactly this, so the line and the chips cannot name one person two ways; it says `No recipient` when there is none, because Send is disabled without one and a silent folded line would leave a dead button with no visible reason. And it **names the sender only when more than one identity is usable**, which is the condition `IdentitySelect` already draws a menu on. A leave guard covers a folder click, the ✕, and the browser Back button, offering a three-way choice — Save draft, Discard, Keep editing — before it discards unsaved content. Its `dirty` means **changed since open or since the last save**, not "form is non-empty": a resumed draft opens clean, and a From-only edit to it is a real change on its own, since silently keeping the old sender would send from the wrong address. A drafts-role folder opens its rows in the composer instead of the reader, re-staging the draft's attachments under the account; its rows show the recipient ("To:") in place of a sender and carry a "Draft" badge, since there both the sender and "sent" are misleading. Sending a resumed draft deletes the filed copy once the send succeeds — it would otherwise be a duplicate of a message that already left. **Search** is: a loupe opens a quick bar (subject OR sender) in the list heading, an advanced popup adds per-field criteria plus an all-folders scope, and results page in place of the normal list. **Contacts** is a real module: a scope band, a searchable tile list, a reading card and a full-width editor on its own routes, plus the address suggestions the composer's recipient fields draw from the same book. Calendar is still a placeholder (`ComingSoon`) page; the settings module is fully built out.

The codebase is a JS/TS mix: new code (router, layouts, contexts, `AccountPage`, `AppearancePage`, `lib/accountIdentity.ts`) is TypeScript (`.tsx`/`.ts`); older ported pages (`AliasesPage.jsx`, `RulesPage.jsx`, the admin tabs, `api.js`) remain JavaScript. Both are typechecked/linted together; there is no plan to force-convert the JS files.

## Design & UX

**`website-design.md` (repo `src/frontend/`) is the reference for the site's look and interaction conventions** — the token foundations, page layout, the tile layout every on-page list follows, buttons and row actions, the dialog rules (the ✕ as the only dismissal, icon continuity between a trigger and its title), the two live-search shapes, the application shell (the dark L, the rail, the band-stack column layout), and the mail module's look — the two "selected" languages (navigation fill vs. content accent bar), the two icon-button hover languages, hover-revealed controls in reserved space, and the folder-tree / message-list / reader conventions. The Administration tabs, the Identities page and the mail module are its reference implementations. Read it before building or restyling any screen, and reuse its classes rather than inventing a local variation.

**A dialog sizes to its content, never to a pixel count** (`src/styles/modal.css`, imported after `index.css` and before `mail.css`). `.modal` is `width: max-content` between `--modal-w` (24rem, the floor) and a viewport guard; what actually bounds it is the prose's own `max-width: 56ch`, since a box's intrinsic contribution is clamped by its child's max-width. Form controls declare no intrinsic width of their own — `flex-basis: 0` in `.field-h`, `width: 100%` in `.field` and `.rule-wizard-input` — so each idiom is amended under `.modal` to take a `--field-w` measure (34ch), which puts every plain form dialog at 433px. **The measure is a `width`, never a `flex-basis`**: measured in Chrome, a basis does not feed the flex container's intrinsic contribution at all, and the first implementation shipped with `--field-w` having literally no effect. **One amendment per idiom rather than one blanket selector, and that is a cascade constraint, not a style choice**: written with `:is()` a single selector overrides `.folder-pick-filter` and `.quota-field`, and written with `:where()` it loses to `.field-h input { flex: 1 }` and leaves every form on the floor. **A `<select>` is exempt** — its widest option already is the measure, which is why `SystemFoldersModal` lands at 516px unaided, and forcing `--field-w` on it made that dialog narrower than the folder names it lists. Two rules exist only for the quota row: `--field-w: 58ch` on it, because a range input's intrinsic width is a fixed ~129px whatever it controls, and `flex: none` on its number box, because `.field-h input[type="number"] { flex: 1 }` is a *descendant* selector and had always been handing it a grow factor — harmless at 250px, a 208px number field at 438px. **The scroll is on `.modal-overlay`, never on `.modal`** — a scroll container clips absolutely positioned descendants, which is what used to cut off the folder picker's dropdown — and the overlay centres with `margin: auto` on the child rather than `align-items: center`, so a dialog taller than the viewport anchors to the top and stays reachable. Do not reintroduce a per-dialog width: a new dialog declares `--field-w` on the row that justifies it, or nothing at all. `styles/modals.test.ts` fails the build if a `.modal` root regains an inline width; nothing else here is assertable, since jsdom computes no layout. **Below 640px that contract has one exception, and only one**: `min-width` always beats `max-width`, so the 24rem floor put a 384px dialog in the 312px a 360px screen leaves inside the overlay — and because the overlay carries `overflow-y: auto`, CSS Overflow 3 forces the other axis to `auto` too, so the symptom was never a scrolling page but a dialog wider than the screen inside an overlay scrolling sideways to reach it. `modal.css`'s phone block drops the floor to 0 and gives `.modal` `width: 100%`: on a phone a dialog takes the screen it is given. The content-sized contract above is untouched at every other width, and the scroll stays the overlay's.

**Three tiers, two widths, and the cascade runs one way only.** Phone is `max-width: 639px`, tablet is the band under `max-width: 1023px` above it, desktop is everything from 1024px up — and **desktop is the unqualified base rule**, not a tier with a query of its own. `1023px` and `639px` are therefore the only two `@media` width values in the whole stylesheet set, and `@media (min-width: …)` is forbidden outright: a min-width query inverts the cascade, and every desktop rule then has to be read through a filter to know whether it applies. `styles/responsive.test.ts` enforces all of it as text — a third width, any `min-width` query, or `min-width: 1024px` returning to `.app-shell` (it was removed; a shell with a desktop floor makes a 360px page scroll sideways whatever else is fixed) each fail the build. The two tokens the phone tier introduces are declared **once**: `--touch: 44px` on `:root` in `shell.css`'s phone block — the test pins it there — and `--toggle-bleed: 12px` in `index.css`'s, which `.rule-card-header`'s and `.rules-toolbar`'s row-gaps are computed from rather than repeating. A second declaration of either is what goes stale the day the first is retuned. `useViewport` (`src/hooks/useViewport.ts`) mirrors those same two widths in JavaScript and is the only place they exist there; it decides **what mounts** — which pane, whether the splitter exists, whether the context pane is a drawer — and never how wide anything is, because a width computed in JS is a second source of truth beside the stylesheet and the two drift.

**When the subject is a column rather than the window, the query is a `@container`.** Two of them exist, both `inline-size`, and both because the column's width and the window's are routinely different numbers: `.mail-list`, whose `@container (max-width: 480px)` drives the selection toolbar's two states — the splitter hands that column anything from its 240px floor to 960px under `readingPane: 'none'`, on the same tablet — and `.mail-reader`, whose header stacks under the same 480px. **The list has one threshold, and the number to read it against is 380, not the 240px floor**: `usePaneSize('mail.split.right', 380, 240)` is what a stock desktop draws, so 480 fires there. That is right for the archive/junk/delete group, measured at 48px of overflow without it. **The master checkbox is not in that group and answers to no width at all** — it is drawn at every column width, and `styles/responsive.test.ts` scans every `@container` body in `mail.css` for it rather than the 480 one alone. It is the only door into the selecting state those actions appear in that anything on screen announces; the other is long-press, which by its nature announces nothing. It had a lower threshold of its own for one branch, hidden below 360, and that is what the rule replaced: a 390px phone could tap the master and watch archive/junk/delete appear, a 360px phone — one of the commonest Android widths — could not. Keeping it costs nothing **at or above the 320px viewport this product supports**, and that bound is the claim rather than "at every width". A column narrower than the viewport is the splitter's doing and the splitter exists only above the phone tier (`effectivePane(…, 'phone')` is `none`, which draws no splitter and hands the list the whole viewport), so `--touch` does not apply to one and the master is the 13px box the browser paints: measured at the 240px floor, the idle toolbar still fits on one row with the folder name ellipsised. On the phone tier the column **is** the viewport, `--touch` does resolve, and the 44px master fits down to a 274px column and no further — measured, 274 clips 0, 260 clips 14, 240 clips 34, with the star painted over `.selection-actions` rather than wrapped, because `.selection-heading` is `flex: 1` from a 0 base and is crushed instead of breaking the line. No shipping device is under 274 (the Galaxy Fold cover screen is 280), but page zoom reaches it — a ~520px window at 200%, Chrome for Android's zoom setting on a 360px handset — so that crush is **out of contract, not impossible**, which is what any future 44px floor on this control (the 640–1023px touch tablet, where `--touch` does not resolve) has to handle along with the heading's shrink. `probes/mobile-layout.html`'s `toolbar-master-380`/`-360`/`-240` trio is that geometry — all three read a box, and `none rendered` on any of them is the regression. The reader's is the measurement of Task 14's full pass rather than a symmetry: on a tablet `.is-right .mail-reader` sits at its own 320px min-width while `.reader-actions` spends 212px of it, leaving `.reader-stack` 64px, so the unsubscribe pill — `white-space: nowrap`, 141px — hung 77px outside a column that is `overflow: hidden` and was cut off rather than scrollable, at 768px and at 1024px alike. **Stacking the header also moves what `align-self` on `.reader-actions` means**, and that cost a shipped defect: the base rule's `flex-end` anchors the cluster to the last line of the stack beside it, which once the header is a column decides left-or-right instead, and `flex-start` put reply/forward/delete/kebab against the left margin at every width the container query matches — the phone block's copy included, since it is the earlier of the two. The pair is `align-self: stretch` + `justify-content: flex-end` and not simply `flex-end`, because an aligned item is shrink-to-fit: max-content while the cluster fits, the full available width once it stops, and at that point its own lines pack from the left again, so the wrapped 320px case would quietly return to where it started. `probes/mobile-layout.html`'s two `reader header` cases carry the rects — `.reader-actions`' right edge must land one 22px padding inside `.reader-header`'s, at all four sizes. **480px is not a third breakpoint and must not be "corrected"** to satisfy the two-width whitelist; the test scans `@media` only, for exactly this reason. Both containers hold dialogs with no portal anywhere in the codebase, and `probes/mobile-layout.html` keeps a case per container proving their `position: fixed` overlays still measure the viewport rather than the column — read the two rects there, never the `intersect` boolean, which is degenerate on a zero-height column. **That evidence is Blink's, not the spec's, and this branch now leans on it twice**: `container-type: inline-size` *does* apply layout containment, which by CSS Contain makes the element a containing block for fixed descendants — Blink simply lays the fixed child out against the viewport anyway, and `elementFromPoint` confirms no z-index trap either. It holds in the browser this product is used in and is measured on every probe run; a third container, or a port to another engine, is where it stops being free.

**When the subject is the finger rather than the window, the query is `@media (hover: none)`.** It carries no width, so the two-breakpoint whitelist has nothing to say about it, and three files now use it: the mail row's and the contact tile's hover-revealed clusters, `.contact-scope`/`.pane-item`'s floors and `.palette-zoom`'s permanent reveal. The distinction is a shipped regression, not a preference: those cluster rules began life inside `@container (max-width: 480px)`, where `usePaneSize('mail.split.right', 380, 240)` puts an ordinary **desktop** list column at 380px — so every mouse user who switched `mail.rowActions` on lost the row cluster entirely, and it survived several review rounds because nothing width-shaped was wrong. A width-keyed rule whose real subject is touch also misses the other end: the 640–1023px touch tablet, where `--touch` does not resolve at all, which is why the `hover: none` copies spell `44px` out. Neither condition contains the other, so both copies are live and neither is a duplicate.

**Geometry is verified in `probes/mobile-layout.html`, never in jsdom** — jsdom computes no layout, so no test in this repo can see a control cut off a column. It links the real stylesheets and restates the markup, needs no session (the dev API carries no `localhost` origin, so a local build cannot sign in), and is driven in a Blink browser — Chrome or Edge — at 360×640, 390×844, 768×1024 and 1024×768, with 320×640 and 540×900 for the cases whose own comments name them. **A fixture that is not the component's markup is not a guard, attributes included**: a bare `<input />` standing in for `RecipientsField`'s `type="text"` reported "byte-identical" through the whole of Task 11 while `index.css`'s phone-block floor on typed controls — an attribute selector, which matches the written attribute and not the IDL default — was pushing the real recipients box from 32px to 54px. Read `clipped` and not `overflow` inside the mail columns, which are all `overflow: hidden`; read `smallest`, which is the lesser of a target's width and height, since a rule that fixes one axis passes a height-only check. **Two touch-target gaps are formally deferred and their non-zero numbers are not rot**: `compose-360` reads `undersized: 7` folded and `compose-360-expanded` 22, the composer's 31px-wide format buttons — it read 14 before the overflow group, so folding paid off half the deferral and no more, and 44px is arithmetic rather than an untried idea, seven cells at 44 coming to 308px plus gaps against the 288 a 320px screen leaves inside the bar's padding; the inset-`::before` hit area `.reader-back` uses does not transfer either, because `.compose-tool-group` packs its buttons 1px apart and the pseudos would steal each other's taps. And `compose-remove-buttons-360` reads `undersized: 2`, the recipient-token ✕ at ~11×18, where the token is deliberately 22px tall and the box wraps tokens on a 4px gap. Both want fewer visible controls still, which is a product call. **`escape` is what `clipped` cannot be**: `scrollWidth - clientWidth` only grows from content past the *right* edge in a left-to-right document, so a right-aligned row that overflows spills LEFT and reads clean. The leave dialog shipped that way — `Continuer l'édition`, `Abandonner` and `Enregistrer le brouillon` come to 440px against the ~310 a 360px screen leaves inside a dialog, and `.folder-pick-submit` is `justify-content: flex-end`, so the first button sat at x=-130 with every number in this file at 0. It now reports the worst overhang per edge across **every** match of its inner selector, which is half the point: the box that escapes is rarely the container a rule names, and aiming it at the row rather than at the buttons inside it reported four clean zeroes for the same broken dialog. A dialog's actions stack and take the width below 640px rather than wrapping, because a `.btn` neither shrinks nor wraps its label — a wrapped row overflows again the day one button alone is wider than the dialog. **`contrast` is the one metric there that is not geometry at all**, and it exists because a colour bug shipped that every other number called clean: `.actionbar-item.is-danger` took `color: inherit`, which walks the parent chain rather than the sibling rule, so the delete cell got the reader column's `--text` and measured **1.09:1** on the action bar's rail background in the light theme — while dark's `--text` happened to land at 14.41 and hid it from anyone checking one theme. A case naming a `contrast` selector is therefore drawn **twice**, once per theme, and reports the worst match's ratio against the background it is actually painted on. Read both numbers; 4.5 is the floor for the small text these cases hold. The action bar is the only place in the app where content sits on the rail's background outside the rail itself, which is why nothing else was there to make the mistake obvious. **`height` is the one metric there with no pass mark**: a case naming a `height` selector reports that element's own box height, because the defect the reader header had was vertical — a header eating the body's screen is invisible to `overflow`, `clipped` and `smallest` alike. Compare it between two runs, never against a threshold. Driving the page needs device-metric emulation and not `--window-size`, which the platform clamps: both 360 and 320 came back as a 518px viewport, and every case silently measured the wrong width.

### Shared idioms and cross-module state

**A settings row is `.field-h.is-setting`, not a bare `.field-h`.** The base was drawn for the admin dialogs — a narrow box with one-word labels, so a 110px label column and the control on `flex: 1`. A settings page is the opposite shape: a wide column with sentence-length labels, and eventually twenty rows rather than two. The modifier widens the label column to 260px and lets a `select` size to its own widest option, so a page-size picker is as wide as "100" instead of as wide as the page.

**A row that explains itself wraps its `<label>` in `.setting-label` and puts the prose in `.setting-hint`** (`GeneralPage` is the reference; `ApplicationTab` still uses the bare modifier, where one-word labels read fine in the inherited uppercase). Three things about it are load-bearing. **The hint sits outside the `htmlFor` label, never inside it** — inside, it joins the control's accessible name, and the switch stops being called what the page calls it, taking every `getByLabelText` with it. **The wrapper is what the width rule targets** (`.field-h.is-setting > .setting-label`), because `.field-h > label:first-child` matches an element, so the reading-pane row's `<span>` first child used to receive no styling at all and was the one label on the page out of line with its neighbours. And **a description is permanent, not conditional**: the remote-images note used to render only while the setting was on, so the page shifted by its own height under the finger that had just flipped the switch.

**`.is-child` indents on the label, `.is-stacked` gives the row to its control, and both were measured rather than reasoned.** A setting that only means something while its parent is off is indented and greyed (`.is-covered`) rather than withheld, since its stored value is what comes back when the parent goes off again — but the indent lives on `.setting-label` as padding plus an absolutely positioned rule, because indenting the row itself pushed the label column 34px right and took that one switch out of the column every other switch stands in. `.is-stacked` exists for a control too wide for the 300px label column: the three reading-pane cards need 293px against the 244px the column leaves inside `.account-section`'s 560px, and they overran its right edge by 49px. Check a layout change in a browser — jsdom sees no geometry at all, so no test in this repo can catch either of those.

**The mail dialogs are built from the admin module's parts**, not their own: `.field-h` rows, `.toggle-switch` for a boolean, one `.btn-primary` submit inside a `<form>` so Enter works, and the ✕ as the only way out — `AddEditUserModal` is the reference. A webmail with two dialects of dialog looks like two applications. Because `.field-h` puts the label *beside* its control rather than around it, every field needs an explicit `htmlFor`/`id` pair; without it the control has no accessible name and `getByLabelText` cannot reach it either.

**Preferences** (`src/hooks/usePreferences.ts`) — shared rather than owned by the settings module, because the message list reads them too. `GET /api/Preferences` answers **every** known key with its default already filled in, so **the client keeps no copy of the defaults**: a consumer waits for the answer instead of guessing, which is why `MessageList` shows "Loading messages…" until they arrive. **That gate does not exist under test**, and the difference has already cost a red CI: `useMessageList` is mocked, so it hands `isLoading` straight in and the rows render before the preferences query resolves. Anything a test asserts that is *derived* from preferences — the list preview, the row's action cluster — must therefore be awaited with `findBy`/`waitFor`, never with `settle()`, which drains a single macrotask: it covered the query on a developer's machine and raced it on the runner, where three assertions read the default set instead of the stored one. `settle()` stays the right tool for its own job, asserting that nothing happened. The stored page-size value is `'10' | '20' | '30' | '50' | '100' | 'all'`, but nothing past `usePreferences` should see the string `'all'` — `requestSizeOf` always returns a number, `BLOCK_SIZE` (100) in streaming mode, and `isStreaming` is the only reader of the raw *stored* value, so a stray `Number('all')` NaN can't be born anywhere else. The literal itself is written once, as the exported `ALL`; `GeneralPage` compares against it to word its toast, but that is the write path, reading the `<select>`'s own value rather than the preferences map. The page size is part of `mailKeys.messages` — a page fetched at 30 per page is a different thing at 100 — and changing any preference invalidates the whole `['mail']` cache for the same reason. The two notification keys (`notifySoundOf`, `notifyDesktopOf`) follow `showPreviewOf`'s pattern in reverse: off unless the stored value is exactly `'true'`, so silence is what an account with no stored preference — or a typo'd one — gets by default. `alwaysShowImagesOf` follows them: off unless the stored value is exactly `'true'`, since a key the backend has not sent yet must keep images blocked. **`mail.rowActions` is the one key that is a set rather than a value** — a comma-separated subset of `seen,archive,junk,delete`, defaulting to the three the row carried before it was choosable — and it is the one place `undefined` and `''` must not collapse: the empty string is an account that switched every icon off, while an absent key is a backend that predates the setting, and reading the second as the first strips every row bare on the first render after a deploy. `rowActionsOf` therefore falls back only on `undefined`, and returns `ROW_ACTIONS` order whatever order the value was stored in, so the setting chooses which icons, never where they sit. The registry backing it needed a mode of its own (`PreferenceDefinition.IsSet`, `UserPreferences.cs`): four icons are sixteen combinations, and enumerating them as allowed values would have hidden the rule inside its own expansion. `MessageReader` **derives** consent (`imagesShown || alwaysShowImagesOf`) rather than seeding its state from the preference — seeding would have to be re-synchronised when the query resolves and re-applied on every message change, and the per-message reset effect would have to learn about the preference.

Shared building blocks live above the module tree: `src/components/` (`Toasts`, `QuotaBlock`/`QuotaMini`, `DeleteConfirmModal`, `Tooltip`, `HelpTooltip`, `ComingSoon`, `LoadingBlock` — the house busy state, a centred `.spinner` carrying `role="status"`/`aria-label="Loading"`, since a spinner has no accessible name and the "Loading…" text it replaces did announce itself), `src/hooks/useToasts.js`, `src/icons/` (one file per icon), `src/lib/accountIdentity.ts` (pure `deriveIdentity()` — derives email/displayName/initials/subDomains from the raw account payload; shared by `AuthContext` and previously inlined in `AliasesPage`). `Tooltip` (`src/components/Tooltip.tsx`, styles in `src/styles/tooltip.css`) is the CSS-only hover bubble extracted from `HelpTooltip`: it wraps any trigger, always mounts its `role="tooltip"` bubble, and reveals it on `:hover`/`:focus-within` with no JS state. Placement is `top-right` (settings, its original spot), `bottom-left` (the mail reader, chosen because that column is `overflow: hidden` and a bubble hanging down-left of the header's leftmost element is the one placement that cannot be clipped), or `bottom-right` (the reader actions zone — the trigger sits flush against the column's right edge, so the bubble opens down-left, the one direction that stays unclippable from that corner too). `HelpTooltip` is now just its `?` icon rendered through it.

## Auth

Session state is **cookie-based**, not a localStorage bearer token — `api.js` sends `credentials: 'include'` on every `fetch` and relies on the backend's `HttpOnly` cookie. `localStorage` only holds a non-secret `sessionActive` flag (`markLoggedIn()` / `clearSession()` / `hasSession()` in `api.js`) so the SPA can synchronously decide whether to attempt rendering an authenticated route before the first API round-trip; the flag carries no auth weight by itself; a stale flag with an expired/absent cookie just gets corrected by the first 401.

`AuthContext` (`src/contexts/AuthContext.tsx`) is the source of truth for the rest of the app:
- `isLoggedIn` — seeded from `hasSession()`, flipped by `syncFromSession()` and by the 401 handler.
- `syncFromSession()` — re-reads `hasSession()`; called by `LoginRoute` right after `LoginPage`'s `onLogin` fires (i.e. after `api.login()` succeeded and called `markLoggedIn()`).
- `logout()` — calls `api.logout()` (best-effort), then always `clearSession()` + `setIsLoggedIn(false)`.
- `account` / `accountLoaded` — populated by `refreshAccount()` (calls `api.getAccount()`), which runs automatically whenever `isLoggedIn` flips true.
- `identity` — `deriveIdentity(account)` or `null` before the account loads.
- `accounts` / `activeAccountId` / `activeAccount` / `accountsLoading` / `switchAccount` — **the multi-account state, no longer scaffolding**. `accounts` is the primary followed by every mailbox the user has attached (`GET /api/ConnectedAccounts`), each `{ id, email, displayName, isPrimary, domainName, credentialsValid, sieveSupported }`. **`activeAccountId` is the id, not the resolved account, and it is what every query key carries**: the id is read straight from `localStorage` at mount while the metadata needs a round trip, so keying on `activeAccount?.id` would send every mail query to the primary mailbox for the width of the accounts fetch and cache the answer under the wrong account. Readers that need the metadata wait on `accountsLoading` instead. `activeAccount` falls back to the primary **only once the list has landed** — during the load window it is `null`, for the same reason. An effect corrects a persisted id whose row came back `credentialsValid: false` or which the list no longer holds, so a stale `localStorage` value cannot strand the session on a mailbox nothing can open. `switchAccount` refuses a target with invalid credentials, and drops the outgoing account's `['mail', id]` queries on the way out so the next visit re-reads rather than showing the previous mailbox from cache.
- `isAdmin` — derived from `account?.isAdmin === true` (also mirrored into `api.js`'s module-level `isAdmin` flag via `setIsAdmin`; `api.js` exposes no public getter for it — the mirror is kept solely because `AuthContext` writes it, not because anything currently reads it back).

**401 handling** — `api.js`'s `request()` calls `clearSession()` and the registered `unauthorizedHandler` on any 401. `AuthContext` registers that handler on mount, setting `isLoggedIn = false` / clearing `account`. Since every authenticated route sits under `RequireAuth`, the next render redirects to `/login` — no page needs to know about auth internals.

**A session ending flushes every cache that outlives it**, in the one effect that reacts to `isLoggedIn` — `queryClient.resetQueries()`, `queryClient.getMutationCache().clear()` and `forgetNotificationClaim()`. The `QueryClient` is a module singleton, so nothing else empties it short of a page reload, and the query keys are account-scoped, but every account of one *session* is still another session's to inherit: without this, signing in as somebody else reads the previous user's folders, messages, contacts and preferences straight out of the cache under the identical `'primary'` key — the bug this fixes was exactly that, corrected by an F5 and nothing else. It lives on the `isLoggedIn` transition rather than inside `logout()` for two reasons: the 401 path (an expired cookie, then a sign-in as somebody else) is covered by the same line, and by the time the effect runs `RequireAuth` has already rendered `<Navigate>`, so the readers of what is being dropped are unmounted. **`resetQueries`, never `clear()`**: `clear()` *removes* every query, and a mounted observer whose query leaves the cache is never told — it keeps its last result and never sees another change. `RequireAuth` unmounts the authenticated readers, but `InstallManifest` sits above the router and outlives every session, so `clear()` left it observing a detached query and blind to `['appSettings']` for the rest of the tab: switching the app off no longer withdrew the manifest. `resetQueries` drops the data of every query while leaving them in the cache, and refetches the **active** ones only — the readers just unmounted are inactive, so nothing doomed is refetched, while the manifest's settings come back on their own. The mutation cache is the one thing `clear()` emptied that `resetQueries` does not, hence the second line. The notification claims need their own removal because `localStorage` outlives the tab, not just the cache. **There is one claim per account, not one claim** — `mail.lastNotifiedUidNext.<accountId>`, `CLAIM_PREFIX` in `notify/channels.ts` — because `uidValidity` is unique per mailbox and means nothing across two of them: under a single key, the account with the higher `uidNext` banks a value that gags the other's new-mail sound until its own `uidNext` climbs past it. `forgetNotificationClaim()` therefore sweeps **every key carrying the prefix** rather than removing one name, so ending a session clears the claims of all the accounts it touched.

## Localisation

The interface speaks English or French, and which one is settled once, in `LocaleProvider` (`src/contexts/LocaleContext.tsx`), by a chain of four: the account's stored language preference when it names a language, then the `ui_language` `localStorage` mirror, then `navigator.languages`, then `en`. `auto` — the default — and any value a build does not recognise fall through at every link alike, because both mean "this link has no answer", and reading an unrecognised value as an answer would strand an account on a locale the build cannot render. **The mirror stores the preference, `auto` included, never the resolved locale**: an account on `auto` that moves to a French-configured machine has to follow that machine, and mirroring `fr` would pin it to the language of the machine it last signed in from. It exists for the two cases the server cannot answer — the login page, which has no session and therefore no preferences, and the first render, which precedes the answer to `GET /api/Preferences` — which is also why `index.html`'s pre-paint script reads it, exactly as it reads the palette. **It is deliberately not cleared on sign-out.** Everything carrying session weight is dropped on the `isLoggedIn` transition; this carries none — it holds one of `en`/`fr`/`auto` and says nothing about who was signed in — and clearing it would send the login page back to the browser's language on every sign-out, which is the surprise the mirror exists to prevent.

**There is no runtime `fallbackLng`**: `I18N_OPTIONS` (`src/lib/i18n.ts`) sets it to `false` rather than leaving it out, and the two initialisations share that object so a change here cannot apply to the app and not to the suite. A fallback's whole job is to paper over a key present in one catalogue and missing from the other, and `src/locales/parity.test.ts` fails the build on precisely that, namespace by namespace. The two are alternatives, not layers: with the fallback, a missing French string renders in English and nobody ever finds out; without it, the gap is a red test before it ships, which is the trade this project wants. Only the active catalogue is loaded, so neither language weighs on the other's bundle and a language change fetches the other one before it switches.

**`src/locales/keys.test.ts` is the missing-key guard for the `.jsx` files.** `tsconfig.json` sets `checkJs: false`, so the typed `t()` guards `.ts`/`.tsx` only — a mistyped key in `RulesPage.jsx`, `AliasesPage.jsx` or any admin tab compiles clean, and with no fallback it renders as its own key on screen. The test reads the source text instead, resolving every key written as a literal inside a `t(…)` call — both arms of the two-state ternary included — and every `<Trans>` `i18nKey`, against the English catalogue, which parity makes sufficient for both. **What it cannot see is a key that reaches `t()` only as a variable, and that shape must therefore not be written.** `t(labelKey)` with the literal sitting in a table above it, or a helper taking the key as a parameter, is invisible to this guard and to `tsc` alike, and is the one remaining way a key can reach production unchecked. Spell the key out in the file that uses it: that is why `RuleHelpModal`'s descriptions are inlined rather than factored, and why `RulesPage`'s weekday labels are a switch over nine literals rather than a `labelKey` field on an options array.

**`src/test-setup.js` initialises i18next in English, synchronously, against the real catalogues** — `initImmediate: false`, both bundles as `resources`, `I18N_OPTIONS` shared with `lib/i18n.ts`. Nothing is stubbed and no string is invented, which makes the whole suite the English catalogue's coverage as a side effect. The consequence to internalise before touching a test: **a red assertion on visible text means the English catalogue holds the wrong string, and never that the test needs updating.** English is the byte-identity baseline of the whole extraction — an assertion that has to move is a translation that changed a language it had no business changing. The French bundle is loaded alongside English rather than instead of it, so the active language stays English and no existing assertion moves, while a test that calls `changeLanguage('fr')` to exercise locale-following behaviour finds real translations rather than raw keys; production reaches them through `loadLocale`'s lazy import, which a test has no step for.

**Three labels are deliberately untranslated, and all three live in `AppearancePage.tsx` rather than in a catalogue.** `English` and `Français` are each written in their own language, because a francophone lost in an English interface does not go looking for "French"; and the palette names (`Night & coral`, `Sea breeze`, `Ink`, …) are product names rather than prose, so only the `{{name}} (default)` suffix around them moves. Keeping them out of the catalogues is what stops `parity.test.ts` demanding a French `Français` and a translator helpfully improving `Ink`.

**French typography is enforced rather than trusted to whoever is writing** — two sweeps in `parity.test.ts`, over every leaf of every French bundle. A no-break space (U+00A0) goes before `; : ? !` and inside `« »`, and that is layout rather than taste: a plain U+0020 there is a legal break point, so a long interpolated value wraps between an opening guillemet and its own content, or leaves a `?` stranded at the head of a line. And the apostrophe is `’` (U+2019), never the ASCII `'` that English keeps in its own nine strings. Both sets of fixtures come in pairs — one string that must match the pattern, its visual twin that must not — because the two spaces are indistinguishable on screen and the two apostrophes nearly so, so whichever one an editor silently normalises, one of the two assertions reddens.

**French was measured in a browser, not reasoned about, and one container had to move.** The settings navigation is the tightest surface and its numbers are recorded with the nav itself, above; French turned out to be the *shorter* language there. Everything else cleared its box, most of it comfortably: `Signaler comme indésirable` takes a 212px quick-action chip against `Report as junk`'s 134px and the four still come to 556px inside `.account-section`'s 560px — and would simply have wrapped if they had not, which is what `.action-chips`' `flex-wrap` is for; the composer's `Enregistrer le brouillon` (145px of text against `Save draft`'s 64px) puts its header row at 483px of the 752px a 1024px window leaves it; and the advanced-search dialog stays at 433px in both languages, because the widest French date option is 174px intrinsic where the `34ch` text fields already spend 257. The one that did not was `EmptyFolderBanner`: `Vider les indésirables maintenant` is 189px against `Empty junk now`'s 92px and the link is `flex: none` — it has to be, since an ellipsised action names a different action — so it ran past a narrow list column's right edge, and `.mail-list` is `overflow: hidden`, so it was cut off rather than scrollable. It now carries `flex-wrap: wrap`, which costs nothing above 320px and gives the link its own line below. **The harness that measured all of this is `probes/localisation-widths.html`**, served by `npm run dev`: it loads the real stylesheets, reproduces each target's markup with its real class names, and fills it with strings imported from `src/locales`, so a catalogue edit changes what it reports. It needs no session, which is what makes it usable at all — the dev API carries no `localhost` origin, so a locally served build cannot sign in and none of these surfaces is reachable behind the auth gate. Reach for it before translating into a third language; no test in this repo can stand in for it, since jsdom computes no layout.

## Testing

Test files sit next to what they test (`Foo.tsx` → `Foo.test.tsx`, `Foo.jsx` → `Foo.test.jsx`), no separate `__tests__` tree. `src/test-setup.js` is the Vitest `setupFiles` entry (jest-dom matchers). One gap worth naming, since no file records it: `src/pages/LoginRoute.tsx` (routing glue) has no dedicated test — it is exercised indirectly via navigation-flow tests.

**Named exports for tests — no longer a blanket rule.** The old convention ("every component under test carries a named `export` in addition to the default") is gone as a project-wide requirement. Shared, genuinely reusable pieces were extracted into their own files under `src/components/`/`src/hooks/`/`src/lib/` (Task 3) and are imported directly by whatever tests them — `AliasesPage.jsx` itself now has **only a default export** since its sub-components (`AccountPanel`, `ChangePasswordModal`, `QuotaBlock`, `Toasts`) were extracted or retired. Large page-local files that still bundle multiple sub-components in one module (`RulesPage.jsx`, the admin tab files) keep named exports alongside their default export purely so their tests can mount those sub-components in isolation — that's a per-file pragmatic choice now, not a house rule.

**No test lost without a replacement.** When moving/renaming a component (a `git mv`, an extraction, a retirement), the tests that covered its old behavior must keep covering it — either by moving with the file or by being folded into the destination's test file. A refactor that reduces the total assertion count on a behavior without an explicit reason is a regression, not a cleanup.

## Deployment

**Pushing deploys — there is no manual release step.** `.github/workflows/deploy.yml` runs on every push: it detects that `src/frontend/**` changed, runs this project's CI (lint, typecheck, tests, build), and only then uploads `dist/` over SSH into `/var/www/admin/mail/account.frontend`. The target environment follows the branch — `prod` on `master`, `dev` on anything else, so a push to a feature branch lands on `account-dev`.

The former `ship-frontend` skill and the local `npm run deploy` / `npm run ship` scripts are gone. The old script uploaded the **whole project** rather than `dist/`, and hard-coded one machine's absolute path — running it would have overwritten the docroot with source files. Deploy by pushing.
