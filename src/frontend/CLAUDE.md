# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`frontend` — a React SPA webmail for the weesky.net mail service (mail, calendar, contacts modules plus a settings area covering account, appearance, aliases, mail rules, and admin). It talks to a backend at `https://api.mail.weesky.net`. **Mail is built for reading**: folder tree with management, paginated message list, reading pane with attachments — a non-inline image attachment's chip splits into the plain download button plus a chevron opening a Download/View menu, the latter loading the image into a small modal viewer rather than a bare `<img src>`, since the API's session cookie would not follow a cross-origin image request — the two flags a reader actually sets — read/unread and star — and message actions — move, copy, archive, report as junk, and delete (a move to trash, or, inside trash, a confirmed permanent expunge). The list also supports **multi-select** (checkbox selection with a persistent bulk-action toolbar) and **emptying a folder** (purge trash/junk, or move everything out to another folder). **Composing** lives at `/mail/compose`, reached by the pencil, first among the selection toolbar's actions: it replaces the message list and reader while the rail and folder tree stay put, so a folder is always one click away without leaving the draft's screen. The body is a WYSIWYG HTML editor (Squire) behind a formatting toolbar; To/Cc/Bcc are token fields, with Cc and Bcc revealed on demand rather than shown by default. Attachments stage on pick — each file starts uploading the instant it is chosen, and the send request carries only the staged ids, never the file bytes. The whole compose surface, not just the attachment tray, is a drop target: dragging a file anywhere over it stages it, with a counter (not a boolean) tracking dragenter/dragleave so the overlay survives the pair firing at every child boundary. An image pasted onto, dropped on, or chosen from the toolbar's image button for the message body becomes an inline part rather than an attachment — `.compose-body` is the drop zone that tells the two apart from the surface around it, and the button is the keyboard and touch way in that paste and drop cannot be; all three land in `routeFiles`, the one place a file is sorted into body or tray — and is resized afterward with **Squire's own eight handles**, which write `style.width` plus `height: auto` onto the `<img>`; the size lives in the markup rather than in React state, so it survives a draft save and reopen (the outgoing sanitiser keeps the inline style, asserted in `OutgoingMailSanitizerTests`, and the resumed draft comes back through that same sanitiser). `insertImage` additionally writes `max-width: 100%`, the bound that stops an unresized full-size photo overrunning the recipient's column, and `.compose-editor` carries `position: relative` because Squire appends its handle container into that root and offsets it by the root's own `scrollTop`. **A bespoke three-width bar (Small/Best fit/Original) was built and removed; do not re-add it**: `squire-rte` constructs its `ImageResizer` unconditionally — there is no config flag — so a click on an image draws Squire's handles over any selection UI of ours, and appending them into the editor root is a DOM mutation Squire's own MutationObserver reports as an `input`, which closed the bar before it ever painted; dragging the native handles then wrote a `style.width` that beat the bar's `width` attribute anyway. That same spurious `input` still marks a resumed draft dirty on a bare click, a Minor left deliberately unfixed: the obvious guard — comparing `getHTML()` before forwarding `onChange` — must not be used, because `getHTML` detaches `.squire-image-resize-container` from the root to serialise the body and re-appending it drops the pointer capture a drag rides on, breaking the very resize it was meant to observe. The drop overlay's `pointer-events: none` is load-bearing: without it the overlay would sit between the cursor and `.compose-body`, covering the very target it announces and routing every image into the tray instead. Sending goes out over SMTP and best-effort files a copy in Sent; a failed copy still reports the send as sent. A "Save draft" button sits beside Send; a leave guard covers a folder click, the ✕, and the browser Back button, offering a three-way choice — Save draft, Discard, Keep editing — before it discards unsaved content. Its `dirty` means **changed since open or since the last save**, not "form is non-empty": a resumed draft opens clean, and a From-only edit to it is a real change on its own, since silently keeping the old sender would send from the wrong address. A drafts-role folder opens its rows in the composer instead of the reader, re-staging the draft's attachments under the account; its rows show the recipient ("To:") in place of a sender and carry a "Draft" badge, since there both the sender and "sent" are misleading. Sending a resumed draft deletes the filed copy once the send succeeds — it would otherwise be a duplicate of a message that already left. **Search** is: a loupe opens a quick bar (subject OR sender) in the list heading, an advanced popup adds per-field criteria plus an all-folders scope, and results page in place of the normal list. **Contacts** is a real module: a scope band, a searchable tile list, a reading card and a full-width editor on its own routes, plus the address suggestions the composer's recipient fields draw from the same book. Calendar is still a placeholder (`ComingSoon`) page; the settings module is fully built out.

Commands live in `package.json` scripts. Tests use Vitest + jsdom + `@testing-library/react`.

The codebase is a JS/TS mix: new code (router, layouts, contexts, `AccountPage`, `AppearancePage`, `lib/accountIdentity.ts`) is TypeScript (`.tsx`/`.ts`); older ported pages (`AliasesPage.jsx`, `RulesPage.jsx`, the admin tabs, `api.js`) remain JavaScript. Both are typechecked/linted together; there is no plan to force-convert the JS files.

## Design & UX

**`website-design.md` (repo `src/frontend/`) is the reference for the site's look and interaction conventions** — the token foundations, page layout, the tile layout every on-page list follows, buttons and row actions, the dialog rules (the ✕ as the only dismissal, icon continuity between a trigger and its title), the two live-search shapes, the application shell (the dark L, the rail, the band-stack column layout), and the mail module's look — the two "selected" languages (navigation fill vs. content accent bar), the two icon-button hover languages, hover-revealed controls in reserved space, and the folder-tree / message-list / reader conventions. The Administration tabs, the Identities page and the mail module are its reference implementations. Read it before building or restyling any screen, and reuse its classes rather than inventing a local variation.

## Architecture

**Routing** — `react-router-dom` v6, `createBrowserRouter` defined in `src/routes.tsx` (the route table lives there). `MailLayout`, `ContactsLayout`, `AliasesPage`, `RulesPage`, and `AdminPage` are `lazy()`-imported in `routes.tsx` and wrapped in `<Suspense fallback={null}>` at the route level, so the shell/settings chrome never waits on their bundle.

**Mail selection lives in search params, not route segments.** A folder path may contain `/` — the hierarchy separator is whatever the IMAP server uses — which is the same reason folder paths travel in the query string or request body on the API side rather than in a route segment. `/mail?folder=INBOX&uid=42` keeps deep links and the back button working under any separator. Choosing a folder drops `uid`, because a message id means nothing in another folder. **`MailLayout` opens the inbox when the URL names no folder** — found by the resolution chain's `inbox` role, not by matching the name, and written with `replace` so Back leaves the mail view instead of bouncing off the redirect. It never selects a message: that stays the user's call.

**`RequireAuth`** (`src/layouts/RequireAuth.tsx`) — reads `isLoggedIn` from `AuthContext`; redirects to `/login` if false, otherwise renders `<Outlet/>`. Everything except `/login` sits behind it.

**`RequireAdmin`** (`src/layouts/RequireAdmin.tsx`) — reads `isAdmin`/`accountLoaded` from `AuthContext`; renders nothing while the account is still loading (avoids a flash-redirect), then redirects non-admins to `/settings/account`.

**Shell layout** — `AppShell` (`src/layouts/AppShell.tsx`) renders `TopBar` + a body split into `AppRail` (left icon rail: Mail/Calendar/Contacts + a spacer + Settings gear, `NavLink`-driven active state) and `<main className="app-content"><Outlet/></main>`. `TopBar` (`src/layouts/TopBar.tsx`) carries the logo/wordmark and nothing else. **The account block is not in the topbar**: `IdentityMenu` (`src/layouts/IdentityMenu.tsx`) sits at the foot of the mail folder column, showing the initials pill, display name and email on the band itself, with a chevron opening a menu **upward** (outside mousedown and Escape close it) that lists every connected account and Sign out. **The menu is the account switcher**: a row calls `switchAccount`, the active one carries a tick, and one whose stored credentials no longer decrypt carries a `Password needed` chip and refuses the click — the fix is on `/settings/connected-accounts`, not here. On a connected account the band itself gains a second line naming the mailbox, so the column always says which mailbox is being read. It carries no Settings entry — the rail's gear is the single route there. Because it lives in the folder column, signing out is reachable from the mail module only; that is the accepted cost of putting the identity where the user reads.

**Mail module** — `MailLayout` (`src/modules/mail/MailLayout.tsx`) builds its own three columns inside the shell's single outlet, the same way `SettingsLayout` does: `.mail-folders` (folder tree plus management), `.mail-list`, `.mail-reader`. `/mail/compose` is a second route pointed at the same lazy `MailLayout`, not a layout of its own: `useMatch('/mail/compose')` swaps `.mail-list`/`.mail-reader` for `ComposeView`, itself `lazy()`-imported a second time so a plain reading session never downloads `squire-rte`.

**Every column is a band stack, not a scrolling box.** Each is `display: flex; flex-direction: column; overflow: hidden`, with exactly one band carrying `flex: 1; min-height: 0; overflow-y: auto` and the rest `flex: none`. That is what keeps the folder actions, the list heading, the pager and the attachment row on screen — all four used to sit at the end of their column's content and had to be scrolled to. **`min-height: 0` is the load-bearing part**: without it a flex child refuses to shrink below its content height, the scroll lands on the column instead of the band, and the pinned bands drift away again.

Files under `src/modules/mail/`:
- `folders/FolderTree.tsx` — hides unsubscribed folders **except the inbox** (Dovecot reports `INBOX` unsubscribed; the flag is meaningless for a folder that is always available), splits the top level into two blocks with a rule between them (`splitByRole`), refuses to select a container-only folder, and suppresses the unread badge on trash and junk — an unread count there prompts reading nobody wants to do

**The role label (`roleLabel`, the i18n seam) replaces the folder name in the tree and the list header.** In the tree (`FolderTree.tsx`), the real name stays one hover away via `title` on the row; the list header (`MessageList.tsx`) has no such fallback — the role label is all that's shown there. A stale override is signalled in Settings next to the value that discovery now provides.
**The folder column offers no folder management at all** — no create shortcut, no manage link. The column footer carries the account block and nothing else. Folder work is rare next to reading, and everything it needs (a row per folder with a switch, rename and delete, plus the create dialog) wants width a 240px column cannot lay out legibly, so all of it lives on `/settings/folders`, which the rail's gear leads to. `CreateFolderModal` is therefore reached from `FoldersPage` only.
- `folders/CreateFolderModal.tsx` — shared by the column footer and the folders settings page, so the two can never drift into two dialects of the same dialog
- `folders/FolderManager.tsx` — one tile per folder (`.admin-list` / `.admin-list-item`, the site's list skin): visibility, rename, delete, plus their dialogs. Reuses `DeleteConfirmModal`. **The tile carries the indentation, not the name**: its left edge steps in with the depth while its right edge stays put, so the action icons keep one column whatever the nesting — indenting the label alone left the switches in a straight line and read as a misalignment rather than a hierarchy. Every tile's name is bold (tile anatomy), so the role badge alone marks a folder holding a role
- `folders/folderNodes.ts` — `flatten` / `parentOf` / `indent` / `isSystemFolder` / `sortFolders`. `parentOf` strips the leaf name rather than splitting on a separator, which works under any separator because the backend rejects names containing one

**Two folder orders, deliberately different.** The mail column (`FolderTree.splitByRole`) puts the folders holding a role in a block at the top — inbox, drafts, sent, archive, junk, trash, the order a reader reaches for them — then a `<hr>`, then the user's own folders by name. The rule is load-bearing, not decoration: without it the two groups run together and a well-known folder is distinguishable from an ordinary one only by recognising its name, which fails exactly where it matters, on a mailbox holding both "Drafts" and "Brouillons". It is drawn only between two populated blocks, since a rule under nothing reads as a rendering fault. System rows carry `.is-system` (weight, no colour). Everywhere the user hunts for a folder *by name* — the folders list, the create dialog's parent picker, the role selects — `folderNodes.sortFolders` puts the inbox first and then everything by name, system folders **interleaved** rather than grouped, so "Deleted Items" sits between "Courrier indésirable" and "Developpement". It compares with `localeCompare` (`sensitivity: 'base'`): a codepoint sort files every accented name after "Z", and a case-sensitive one exiles "e-commerce" past every capitalised name

**A folder holding a role carries its controls disabled, not withheld** — the switch, the rename and the delete are all on the row, greyed. Hiding one strands whatever gets filed into it; renaming or deleting one breaks the role for every client on the mailbox. Dropping the buttons entirely made those rows a different *shape* from every other one, which reads as a rendering fault; disabled beside the role badge — which sits against the name, not off in a column of its own — the rule explains itself. **The API refuses these three operations too** (`MailController.RefuseIfSystemFolderAsync`), deletion including the target's whole subtree — a guard living in one client is one new screen away from being forgotten

**A settings row is `.field-h.is-setting`, not a bare `.field-h`.** The base was drawn for the admin dialogs — a narrow box with one-word labels, so a 110px label column and the control on `flex: 1`. A settings page is the opposite shape: a wide column with sentence-length labels, and eventually twenty rows rather than two. The modifier widens the label column to 260px and lets a `select` size to its own widest option, so a page-size picker is as wide as "100" instead of as wide as the page.

**A row that explains itself wraps its `<label>` in `.setting-label` and puts the prose in `.setting-hint`** (`GeneralPage` is the reference; `ApplicationTab` still uses the bare modifier, where one-word labels read fine in the inherited uppercase). Three things about it are load-bearing. **The hint sits outside the `htmlFor` label, never inside it** — inside, it joins the control's accessible name, and the switch stops being called what the page calls it, taking every `getByLabelText` with it. **The wrapper is what the width rule targets** (`.field-h.is-setting > .setting-label`), because `.field-h > label:first-child` matches an element, so the reading-pane row's `<span>` first child used to receive no styling at all and was the one label on the page out of line with its neighbours. And **a description is permanent, not conditional**: the remote-images note used to render only while the setting was on, so the page shifted by its own height under the finger that had just flipped the switch.

**`.is-child` indents on the label, `.is-stacked` gives the row to its control, and both were measured rather than reasoned.** A setting that only means something while its parent is off is indented and greyed (`.is-covered`) rather than withheld, since its stored value is what comes back when the parent goes off again — but the indent lives on `.setting-label` as padding plus an absolutely positioned rule, because indenting the row itself pushed the label column 34px right and took that one switch out of the column every other switch stands in. `.is-stacked` exists for a control too wide for the 300px label column: the three reading-pane cards need 293px against the 244px the column leaves inside `.account-section`'s 560px, and they overran its right edge by 49px. Check a layout change in a browser — jsdom sees no geometry at all, so no test in this repo can catch either of those.

**The mail dialogs are built from the admin module's parts**, not their own: `.field-h` rows, `.toggle-switch` for a boolean, one `.btn-primary` submit inside a `<form>` so Enter works, and the ✕ as the only way out — `AddEditUserModal` is the reference. A webmail with two dialects of dialog looks like two applications. Because `.field-h` puts the label *beside* its control rather than around it, every field needs an explicit `htmlFor`/`id` pair; without it the control has no accessible name and `getByLabelText` cannot reach it either.
- `list/MessageList.tsx` + `list/formatDate.ts` — rows between a fixed heading band and a footer; the page index resets when the folder changes. **The footer is the pager's alone, and exists only when there is a page to go to** — paged mode past `lastPage > 0`. Streaming ("All") carries no footer band: it once held a loaded/total counter, which was dropped because a count is what the scrollbar already shows and a permanently non-navigable strip above the list only ate rows. Do not reinstate it as a "you are here" indicator. The preview element is always rendered even when empty, so a bodyless message does not make a shorter row than its neighbours. **The row's hover cluster (`.message-row-cluster`) is built from `mail.rowActions`, in `ROW_ACTIONS` order, and disappears entirely when the account chose none** — an empty cluster would still eat its reserved width. Withheld there is the user's own choice; a button whose role no folder holds is still drawn, disabled, carrying its reason, because *that* absence would read as a rendering fault. The star is not in the set: it is a flag rather than an action, and it lives outside the cluster. The heading band is now `SelectionToolbar` — `MessageList` owns the selection (`useSelection`) and the bulk actions (move/copy/archive/junk/delete/mark read-unread/empty), wiring role-aware enablement and the empty-folder confirm into the toolbar and `EmptyFolderBanner` it renders below

- `list/searchCriteria.ts` — `SearchCriteria`/`AdvancedForm` shapes and the pure helpers (`criteriaFromForm`, `labelOf`, `isEmptyCriteria`, `isStarredOnly`) shared by the bar, the modal and the query layer

**The star beside the folder name is a search, not a second filtering mechanism.** It writes the same `flagged` criterion the advanced form's checkbox writes, on the search already running when there is one — so the icon and the checkbox are two doors onto one state and can never contradict each other. Switching it off drops `flagged` and keeps the rest, clearing the search entirely only when nothing else remains. Two things follow, both wanted: the search is same-folder, so `crossFolder` stays false and the rows keep their checkbox, their own star and their drag — the user can unstar straight from the filtered list (the row then stays put until the next refresh rather than vanishing under the cursor, since `useSetFlags` patches in place). And "Empty folder" disables itself under the filter through the existing `searching` guard, which is exactly right. `isStarredOnly` is what keeps the results banner away while the filter stands alone: the lit star is the whole indication, so the heading keeps the folder name; add any other criterion, or search every folder, and the banner comes back with its count.
- `list/useMessageList.ts` — answers one shape (`messages`, `total`, `paging | null`, `streaming | null`) whether the reader is paged or scrolling "All", so `MessageList` never learns what "All" means; it renders a pager or a sentinel purely on which of the two came back non-null. `useMessages` and `useMessageStream` are both called on every render — hooks cannot be conditional — with whichever mode is inactive passed `enabled: false`, so it issues no request. A block that fails after others already loaded keeps those rows on screen and offers Retry; "Could not load messages" only appears when the failed block is the first one, because that is the only case with nothing to keep
- `list/messageStream.ts` — `dedupeByUid` exists because paging is a numeric offset: a message that arrives between two block fetches shifts every row after it by one, so the last row of an earlier block reappears as the first row of the next. `nextBlockIndex` stops the stream on a block shorter than the request size, never by comparing loaded count against `total` — `total` moves as mail arrives, so a stream chasing it would either never stop or stop one block short. `sentinelIndexOf` places the sentinel `PREFETCH_ROWS` rows before the last loaded row
- `list/LoadMoreSentinel.tsx` — a zero-height `<div>`; checked in a real browser rather than assumed, an `IntersectionObserver` fires on a zero-area target exactly as it does on a full row, at 20 rows before the end. `PREFETCH_ROWS = 20` is rows, never pixels — row height changes with the preview setting, so a pixel margin would fire at a different message count depending on a toggle that has nothing to do with scrolling. The margin has to stay well under `BLOCK_SIZE` (100): near 80, each arriving block would drop its own fresh sentinel back into view and queue the next block immediately, and the whole folder would load itself
- `list/folderDelta.ts` + `list/useListRefresh.ts` — the folder-move detector and the effect that acts on it; the *why* is in the periodic refresh note below
- `notify/notifyDecision.ts`, `notify/channels.ts`, `notify/useMailNotifications.ts` — the new-mail sound and desktop notification; the *why* is in the notifications section below
- `reader/MessageReader.tsx`, `reader/sanitizeBody.ts`, `reader/formatReaderDate.ts`, `reader/formatSize.ts`, `reader/AddressLabel.tsx` (+`AddressList`), `reader/AuthBadge.tsx`, `reader/authVerdict.ts`

**The reader header is a stack, not a row: subject, then sender + badge + date, then To and Cc.** Each address is an `AddressLabel` — the display name when there is one, the bare address otherwise, with `"Name" <address>` in a bubble only when the label is not already the address (a bubble repeating the text under the cursor is noise). The sender is a `<button>` with no handler yet: focusable so its bubble is keyboard-reachable, and one `onClick` away from opening a composer. To/Cc render only when non-empty, one label per recipient. **The badge is green only when SPF and DKIM both passed, red when one explicitly failed, and absent otherwise** (`authVerdict`) — a `softfail`, `neutral`, or missing verdict paints nothing, because a signal on an ambiguous result teaches the reader to ignore the badge. Its bubble carries a summary line plus the raw `Authentication-Results` header. It reuses `--success`/`--danger`/`--badge-count-fg`; no palette file was touched. `.reader-recipients` is `display: block`, not flex: a flex row makes `To: ` an anonymous item whose trailing space is stripped, so the header would read `To:Mick`. Below To/Cc, `SpamGauge` (`reader/SpamGauge.tsx` + `reader/spamRatio.ts`) renders "Spam score:" with a bar whose single `--gauge-ratio` custom property drives both its width and its `color-mix(in oklab, var(--success), var(--danger) …)` colour — no new token, no literal colour. The line renders only when the message carries a recognised anti-spam header AND `mail.showSpamScore` (on unless explicitly off, read in `MessageReader`, not in the component) allows it. `.reader-spam` is `display: block` for the same trailing-space reason as `.reader-recipients`. The header row is flex: the stack takes `flex: 1` and `ReaderActions` sits `align-self: flex-end` — bottom-right of whatever lines are actually present, since To, Cc and the spam gauge may each be absent. It holds the colour toggle (dark theme + HTML body only; the icon shows the action to come — sun for the sender's colours, moon for the way back, the old banner's texts as tooltips), then a Delete button, then the kebab. **Delete carries two behaviours behind one label**: outside the trash it moves the message to the trash role with no confirmation — the trash folder is the undo — while inside the trash the same button expunges permanently (`\Deleted` + `UID EXPUNGE`) behind a confirm modal; it is disabled with a tooltip when no folder holds the trash role. The kebab, a `DropdownMenu` (`src/components/DropdownMenu.tsx`), holds two groups: mark read/unread and star/unstar, a separator, then Archive / Report as junk / Move to… / Copy to…. The first two entries name the action to come as well, for the same reason the colour toggle does: an open message is read, so its entry has to read "Mark as unread" or the menu is describing a state nobody asked about. Move and Copy both open `MoveMessagesModal`, one filterable folder picker shared between the two modes — unusable rows (the current folder, any non-selectable container) stay listed and disabled rather than dropped, since a folder that goes missing from the list reads as a bug rather than a rule. The colour banner is gone.

**A chevron closes the sender line**, swapping the compact To/Cc lines for `ReaderDetails` — a `<dl>` grid carrying From, To, Cc, the long date, and whatever the backend's `MailHeaderDetailsReader` found: mailing list, mailed by, signed by, unsubscribe, TLS. Each row renders only when its datum exists, and `detailsOpen` resets with the message like the image consent, because it is a look at one mail rather than a preference. **The Security row tests `typeof tlsReceived === 'boolean'`, never `!== null`**: the frontend and the microservice ship through two separate skills in no guaranteed order, and against an older API the absent field is `undefined`, which a `!== null` test renders as "No encryption" on every message — a false negative security indicator. Beside the chevron, an `Unsubscribe` link appears whenever the message carries an **http(s)** `List-Unsubscribe` (`unsubscribeLink.ts`, the single predicate both the header and the grid ask). It sits with the sender because unsubscribing acts on the sender, not on this message — which is also why it is not in the actions zone. A `mailto:` unsubscribe is deliberately offered in the details grid only: following one would leave the webmail for the OS mail client, and there is no composer to hand it to yet.

**The iframe gets a document, not a bare fragment** (`renderBodyDocument`). A fragment inherits the browser's defaults: an 8px body margin that left message text visibly out of line with the header, and a serif face for any body carrying no styles. The wrapper sets padding matching `.reader-header`, contains the two overflows a body can inflict on the layout regardless of intent (`overflow-wrap: break-word` for the long unbroken URLs this mailbox is full of — **never `anywhere`**, which additionally feeds its break points into min-content sizing, collapsing a table column to one letter and rendering a GitHub mail's "Status" heading vertically, `img { max-width: 100% }` — **never `height: auto`**, which recomputes every height from the intrinsic ratio and turned a 1×1 spacer gif stretched to 154×10 by attributes into a 154px tower, wrecking newsletter buttons), and pins `color-scheme: light` with a white background in **every** theme, dark mode included — the inversion below needs a white canvas to turn black.

**Dark mode recolours the message, it does not invert it** (`reader/darkenColours.ts`). Each declared colour has its *lightness* inverted while its hue is left alone, the approach Dark Reader takes: a red button stays red and an Amazon yellow stays yellow. Three rules bound that inversion, and each exists because a real message broke without it. **A background is never lightened and a text colour never darkened** — a section the sender drew black was drawn that way on purpose, and the white logo sitting on it cannot follow when the slab under it turns pale; the bound also rescues light text whose background is declared on an ancestor, which used to come out dark on dark. Because only the half that needs flipping is flipped, every pair still converges on a dark background under light text. **A saturated background is damped** (`BACKGROUND_SATURATION`, `SATURATED_LIGHTEST`) — a brand colour across a slab is what glows on a dark canvas, an Amazon button came back a vivid gold; the damping is proportional to the colour's own saturation, so greys, whites and blacks do not move at all, and text keeps its full strength since a link that loses its colour stops reading as one. **A gradient is a colour wearing an image's clothes**, so `background-image` values have their stops darkened too, with `url()` consumed first so a path that spells a colour is never rewritten. A photograph is still never recoloured; in dark mode `renderBodyDocument` only dims images uniformly (`brightness(0.85) saturate(0.9)`), because the iframe is sandboxed and cross-origin so no pixel can be read to tell a banner from a photograph. A `filter: invert(1) hue-rotate(180deg)` was tried first and is the cheap approximation — it inverts in RGB, so hues drag across the wheel, images need a second inversion to survive, and every white becomes pure black. White lands on the app's own dark surface rather than `#000`, because a black slab beside the app's greys reads as a hole. **Colours are written as hex, never `rgb()`**: `bgcolor` and friends are presentational attributes that do not understand `rgb()`, and the browser's legacy colour parsing salvages the hex digits out of `rgb(84, 22, 0)` and invents a colour from them — a brown background came out green, and a string assertion could not see it. It runs **before** sanitising, like `revealBlockedImages`, so what it writes faces the same pass as the rest. Since it is a rendering choice rather than a faithful one, `MessageReader` offers a per-message way back to the sender's colours, reset on every message like the image consent. The resolved theme comes from `useTheme().isDark` — the preference alone says nothing when it is `system`.

**Two dates, two questions.** The list shows the message's *arrival* (`InternalDate`), because arrival is what orders the list — printing the `Date` header there would put a May date among the June rows and read as a sorting bug. The reader shows the `Date` header, spelled out and without seconds, because there the question is when the sender wrote it.

**The From address is resolved client-side the same way the backend resolves the default, so the two never disagree before a send.** `ComposeView` seeds `fromAddress` at `null` — "no explicit choice yet" — and derives what to actually show/send (`effectiveFrom`) as the chosen address, else the usable list's `isDefault` row, else its first row; `IdentitySelect` **requires** that resolved address as its `value` and never invents one of its own. The component holding the send payload is the only place the fallback may live, so the address on the trigger and the address in the request cannot drift apart. The staged choice is sent as `POST /api/Mail/Send`'s `fromAddress`; the label the recipient sees is never sent along with it — the backend re-resolves it from the stored identity, so a display name edited in Settings between opening the composer and hitting send is what goes out, not a stale one carried in React state.

**The reading pane sits in one of three arrangements, picked by `mail.readingPane`** (right by default; `readingPaneOf` falls back to `right` defensively). `MailLayout`'s root carries `is-right`/`is-bottom`/`is-none` and builds its columns from that: `right` puts list and reader side by side, `bottom` wraps list, splitter and reader in a `.mail-stack` so the reader sits under a shortened list, and `none` gives the list the whole width and hands the screen to the reader only once a message is opened. **In `none` the list is hidden with `.is-hidden`, never unmounted** — its scroll position and the streamed blocks it holds are session state that opening and backing out would otherwise throw away, so it stays mounted behind the reader with the selected uid forced null (no row reads as "open beside" when the reader owns the screen), and the reader mounts with an `onBack` the other two modes never pass — `MessageReader` draws the ← button and binds Escape only when it gets one. The list switches to a `wide` single-line row skin in `bottom` and `none` (sender · subject — inline preview · date on one line) and keeps the two-line row at `right`; both honour `mail.showPreview`, so the inline preview shows or not exactly as it does in the narrow list — one row, two skins. **The splitter sizes are per-device localStorage, never backend preferences** (`usePaneSize`): a 4K screen and a laptop want different splits, so `mail.split.right` (380, min 240) and `mail.split.bottom` (280, min 120) live on the device, not in the account. `PaneSplitter` owns no size — the parent hands one in and hears changes back — so the one bar serves both orientations; it drags to a ceiling of the parent span minus a reserve, nudges by arrow key, resets on double-click, cleans up on `pointercancel` as well as `pointerup`, and carries `role="separator"`.
- `queries.ts` — TanStack Query hooks and keys; `api/mailTypes.ts` — response shapes. `useMessageStream` sets `refetchOnWindowFocus: false`: TanStack's default refetches *every* loaded page on focus, so forty loaded blocks would mean forty IMAP connections and forty full folder sorts on switching back to the tab. `App.tsx` sets that default to `true` app-wide, so an omission here would silently reintroduce it. `useFolders` polls independently — see below — and takes an `enabled` parameter so a caller that has no use for the tree, the notification hook among them, can leave the query off rather than duplicating it. `useEmptyFolder` carries `mailKeys.writes` and, on a move-all, patches the target folder's counts from the source tree node rather than invalidating, the same optimistic-then-poll-reconciles pattern as the other mutations here. `useIdentities`/`useReplaceIdentities` wrap `GET`/`PUT /api/Identities`: the query carries a 5-minute `staleTime` since the list changes only from Settings, and the mutation invalidates `onSettled`, not `onSuccess`, so a refused `PUT` still resyncs the page to the server's copy instead of leaving the optimistic list on screen

**The folder list polls so the open webmail catches up with other IMAP clients within a minute.** `useFolders` sets `refetchInterval: POLL_INTERVAL` (`queries.ts`, 60s — internal like `BLOCK_SIZE`, not a setting) rather than a bespoke timer, so one cheap LIST+STATUS answer refreshes the tree badges and drives the message-list watcher at once, for every folder, not only the open one. TanStack pauses the interval while the tab is unfocused; the app-wide focus-refetch default (`App.tsx`) is the catch-up tick on return, so no separate foreground-poll logic is needed. `MailLayout` wires the watcher in one line, `useListRefresh(folder)`, because the hook reads `useFolders()` itself rather than being handed folder data as a prop.

**`folderChanged` (`list/folderDelta.ts`) trips on four counters because each is blind to what the others miss.** Mail arriving moves `uidNext` and `total`; mail deleted from another client moves `total` but leaves `uidNext` untouched; a flag flipped elsewhere (read/unread, a Sieve rule firing) moves none of the three, since they all describe *which* messages exist, never their state — which is what `highestModSeq` (`HIGHESTMODSEQ`, RFC 7162, CONDSTORE-gated) is for. A server without CONDSTORE answers `highestModSeq: null` forever, so `moved()` requires both sides non-null before comparing: null is tolerated indefinitely, and a null-to-value transition is the server just starting to report the counter (discovery), never treated as a change.

**A `uidValidity` break is answered differently from an ordinary change, and neither path invalidates the stream.** `uidValidity` moving means the server reassigned every UID in the folder — the cache is not stale, it is wrong — so `useListRefresh` calls `resetQueries` scoped to that folder's keys (messages, message and messageStream alike), refetching only what is actually mounted. An ordinary change in streaming mode instead fetches block 0 alone and **merges** it into the cached block 0 with `setQueryData` (`refreshFirstBlock`, `dedupeByUid([fresh, old.pages[0]])`, fresh first). Merge not replace: arrivals shift older rows out of block 0's window and the frozen later blocks do not hold them, so a replace opens a gap dedupe can't refill — the shipped fixture dropped uid 29. Block 0 then grows with arrivals (bounded by the session; `nextBlockIndex` reads only the last page, so pagination is untouched), and a row deleted elsewhere lingers in the merged tail like it does in every frozen block — snapshot semantics. **Neither path ever calls `invalidateQueries` on the stream key** — TanStack's invalidate replays every loaded block, so a reader forty blocks into a folder would cost forty IMAP connections and forty full folder sorts on a single poll tick. Paged mode has no such cost, one page is one request, so there `useListRefresh` invalidates freely. Poll and refresh failures are silent by design in both modes: at a tick a minute, a toast per blip would be unbearable, and the next tick is the retry.

**Scroll is deliberately not compensated.** Rainloop and Outlook Web were both tested by hand for this slice and neither compensates: when mail lands, the rows the user is looking at shift down instead of staying pinned. The reading pane is unaffected regardless — it is keyed by `uid` (`mailKeys.message`), a query of its own, not by list position — so do not reintroduce scroll compensation as a "fix" for something neither reference client fixes either.

**New-mail notifications** (`src/modules/mail/notify/`) ring for the inbox from anywhere in the app — `useMailNotifications` is mounted once, in `AppShell`, not `MailLayout`. The full contract (the `uidNext` trigger and why an already-read batch still has to be gagged, silent re-baselines, two-tab dedupe, permission-beats-preference, the load-bearing `settle()` in its tests) lives in `.claude/rules/frontend-notifications.md`, loaded when working on the notify module, `GeneralPage`, `AppShell` or `queries.ts`.

**Preferences** (`src/hooks/usePreferences.ts`) — shared rather than owned by the settings module, because the message list reads them too. `GET /api/Preferences` answers **every** known key with its default already filled in, so **the client keeps no copy of the defaults**: a consumer waits for the answer instead of guessing, which is why `MessageList` shows "Loading messages…" until they arrive. **That gate does not exist under test**, and the difference has already cost a red CI: `useMessageList` is mocked, so it hands `isLoading` straight in and the rows render before the preferences query resolves. Anything a test asserts that is *derived* from preferences — the list preview, the row's action cluster — must therefore be awaited with `findBy`/`waitFor`, never with `settle()`, which drains a single macrotask: it covered the query on a developer's machine and raced it on the runner, where three assertions read the default set instead of the stored one. `settle()` stays the right tool for its own job, asserting that nothing happened. The stored page-size value is `'10' | '20' | '30' | '50' | '100' | 'all'`, but nothing past `usePreferences` should see the string `'all'` — `requestSizeOf` always returns a number, `BLOCK_SIZE` (100) in streaming mode, and `isStreaming` is the only reader of the raw *stored* value, so a stray `Number('all')` NaN can't be born anywhere else. The literal itself is written once, as the exported `ALL`; `GeneralPage` compares against it to word its toast, but that is the write path, reading the `<select>`'s own value rather than the preferences map. The page size is part of `mailKeys.messages` — a page fetched at 30 per page is a different thing at 100 — and changing any preference invalidates the whole `['mail']` cache for the same reason. The two notification keys (`notifySoundOf`, `notifyDesktopOf`) follow `showPreviewOf`'s pattern in reverse: off unless the stored value is exactly `'true'`, so silence is what an account with no stored preference — or a typo'd one — gets by default. `alwaysShowImagesOf` follows them: off unless the stored value is exactly `'true'`, since a key the backend has not sent yet must keep images blocked. **`mail.rowActions` is the one key that is a set rather than a value** — a comma-separated subset of `seen,archive,junk,delete`, defaulting to the three the row carried before it was choosable — and it is the one place `undefined` and `''` must not collapse: the empty string is an account that switched every icon off, while an absent key is a backend that predates the setting, and reading the second as the first strips every row bare on the first render after a deploy. `rowActionsOf` therefore falls back only on `undefined`, and returns `ROW_ACTIONS` order whatever order the value was stored in, so the setting chooses which icons, never where they sit. The registry backing it needed a mode of its own (`PreferenceDefinition.IsSet`, `UserPreferences.cs`): four icons are sixteen combinations, and enumerating them as allowed values would have hidden the rule inside its own expansion. `MessageReader` **derives** consent (`imagesShown || alwaysShowImagesOf`) rather than seeding its state from the preference — seeding would have to be re-synchronised when the query resolves and re-applied on every message change, and the per-message reset effect would have to learn about the preference.

**Data layer** — TanStack Query, provided in `App.tsx`. This is the only module using it; the settings pages still hand-roll `useEffect`. Query keys are scoped by the active account (`['mail', accountId, …]`), which is what keeps two attached mailboxes from mixing: switching is a change of key, so the arriving account starts on a cold cache rather than on the previous one's folders and messages. Folder mutations invalidate the folder tree, since each of them changes either the hierarchy or the counts it displays; the tree also refreshes on a plain poll (see above), so a change made through another client shows up too, not only one made here. A 401 is never retried — it will not succeed, and retrying only delays the redirect to `/login`.

**Rendering message HTML — three independent barriers.** The backend sanitises the body; `reader/sanitizeBody.ts` sanitises it again with DOMPurify; and it is rendered in an `<iframe sandbox="allow-popups allow-popups-to-escape-sandbox">` — never `allow-scripts`, never `allow-same-origin`. **Never render message HTML into the page itself.** The two popup permissions are load-bearing, not a loosening: a fully empty sandbox withholds navigation too, so the `target="_blank"` links the sanitiser produces silently did nothing on click, and without the escape clause the opened tab inherits the sandbox and the destination site loads broken. The two sanitising passes are not redundancy: the bug class that defeats a sanitiser is a parse divergence between it and the browser, and two passes in different engines mean a body must defeat both. Remote images arrive as `data-blocked-src` and are only restored on consent — per message by default, or once and for all via `mail.alwaysShowImages`, which suppresses the banner entirely. **The preference never enters the sanitising pipeline**: it is read in `MessageReader` and only pre-applies the reveal the button performs, so a body is the same document for every account and the message cache does not depend on it. **A CSS background travels the same road, under `data-blocked-bg`**: the backend moves a remote `background-image` layer out of the CSS into that attribute, and `revealBlockedImages` puts it back — so the button restores background images, and so does the setting, which feeds the same `showImages` flag (`MessageReader.tsx:118`). A withheld background is restored **through CSSOM**, never by concatenating onto the style text, and its scheme is **re-validated here** (`restorable`, http/https only, quotes and backslashes percent-encoded): DOMPurify does not check it — measured, `sanitizeBody('<div style="background-image: url(javascript:alert(1))">x</div>')` returns the declaration untouched — so this client-side gate is not a second opinion on the backend's, it is the only one on this side. A `url(cid:…)` layer the backend left in the CSS is not blocked at all; the `useInlineImages`/`substituteInlineImages` pair resolves it into a data URI from our own API's bytes, after sanitising rather than before, since those bytes are not message markup.

**Contacts module** — `ContactsLayout` (`src/modules/contacts/ContactsLayout.tsx`) builds three columns inside the shell's single outlet, the way `MailLayout` and `SettingsLayout` do: the scope band, `.contacts-list` and `.contacts-card`, with the mail module's `PaneSplitter`/`usePaneSize` between the last two under a key of its own (`contacts.split.right`, 380 default / 240 floor) — per-device localStorage for the same reason the mail splitter's sizes are. `/contacts/new` and `/contacts/:id/edit` are two further routes pointed at the **same** lazy layout, not layouts of their own: `useMatch` swaps the list and the card for `ContactEditView` while the band stays put, exactly the `/mail/compose` mechanism, so a scope is one click away without leaving the form. **A contact id travels in a route segment where a folder path never could** — it is a GUID, so none of the separator trouble applies — but the *selected* contact stays in a search param (`?id=`), because opening a card is a selection while opening the editor is a different surface. Choosing a scope drops the selected id, for the reason choosing a folder drops the uid: a contact filtered out of the new scope must not stay open. Deleting goes through the shared `DeleteConfirmModal`, the module's only dialog.

**The band exists for what lands in it, not for its two rows.** `ContactScopes` carries All contacts and Favourites with their counts and nothing else; `ContactsTransfer` sits in the column's footer under them, separated by a rule, holding `Import…` and `Export` — file actions rather than navigation, which is why they are not rows among the scopes, the same reason the mail column keeps its account block at the foot. Its mutation invalidates `onSettled` like the module's four others, so a refused import still resyncs the book. **The hidden input is cleared before the upload is awaited**: an input that keeps its value fires no change event when the same file is picked twice. `Export` is disabled on an empty book — a file with no rows reads as a failure — and downloads through the shared `lib/downloadBlob.ts`, extracted from `MessageReader` so the two cannot drift.

**`contactName.ts` and `contactSearch.ts` are the module's whole shared surface** — everything else in the folder is a screen. `displayNameOf` is the one place a contact is named (first + last, else nickname, else the first address): the tile, the card, the editor's heading and the composer's dropdown all call it, because four screens naming one contact four ways is the defect it exists to prevent. `primaryAddressOf` is `addresses[0]` and nothing more, since position 0 *is* the primary — the backend stores an order, never a flag, so there is nothing that could fall out of step with it. `fold`/`matches` strip diacritics with `\p{M}` and lower-case, the same normalisation `folderFilter.ts` performs and for the same reason (nobody reaches for the é key to look somebody up); the page's filter and the composer's dropdown call the identical predicate, so the two can never disagree about what "matching" means.

**One address may belong to several contacts, and that is what shapes the autocomplete.** Nothing at any layer forbids it — a household or a shared mailbox is a real contact each — so `suggestionsFor` keys its rows on the **folded, trimmed address** rather than on the contact: one address is one row carrying every name that holds it, because two rows inserting the identical recipient are indistinguishable from a bug. Only the key is canonical; the row still displays the address as stored, so the spelling on screen stays the user's own. Rows sort favourites first, then a primary address ahead of a secondary one, then alphabetically, and cap at ten.

**The composer's field highlights nothing until an arrow says so.** `RecipientsField`'s `active` starts at `-1` and returns there on every keystroke: Enter must commit what the user typed, never substitute a suggestion they never looked at. Escape hides the list without discarding the query, so an arrow brings it back and lands on the end it came from. The `<ul>` preventDefaults its own `mousedown` **on the container**, not per row — a mousedown on the scrollbar or the padding strip blurs the input, and blur commits the half-typed draft as an invalid token. `ComposeView` calls `useContacts()` once and hands the array to all three fields; the prop defaults to `[]`, so an account with no contacts keeps the field's pre-suggestion behaviour exactly.

**One tile skin, on two lines** — star + name + actions, then the address underneath. The message list carries two skins because three pane arrangements exist there; here the list always sits beside the card, so a wide skin would be code nothing can reach. The address line renders even when empty, so an address-less contact is not a shorter tile than its neighbours, and it carries `· +N` when the contact holds more than one.

**The editor waits for the book before it mounts, and an unknown id is not an invitation to create.** `ContactEditView` seeds its state from its contact once, at mount, so mounting it on an edit route before `useContacts()` has answered would seed an empty form that the arriving data would never reseed — `ContactsLayout` holds the loading/error line until the book is in hand. Once it *is* in hand, a route id the book does not resolve is a target that no longer exists (an obsolete bookmark), so the layout toasts and redirects to `/contacts` with `replace`; it used to fall through to create mode, where saving fabricated a second contact. The search-param variant (`?id=unknown`) instead keeps the "select a contact" invite, the way mail treats a vanished message. The editor is keyed on the contact being edited so switching from one edit to another reseeds it, and `saveError` is cleared when that key changes — otherwise a refusal on one contact sits above the next contact's form.

`contacts/queries.ts` — `useContacts()` on `['contacts', accountId]`, scoped by account from the outset like the mail keys, with a 5-minute `staleTime` since only this module writes to it, and sorted in `select` so the page and the composer read one already-ordered list instead of each sorting its own copy. Every mutation invalidates **`onSettled`, not `onSuccess`**: a refused write must leave the screen on server state rather than on an optimistic lie.

**`useAccountId` lives in `src/hooks/`, not in `modules/mail/queries.ts`.** Contacts key their cache on the account too, and a module reaching into another module's data layer for the account identity is a coupling nothing justifies; it moved with all seven of its importers.

The code is the backend's `ResultEnveloppe` message when it is a stable string — `credentials_unavailable`, `Message not found` — so callers branch on a symbol rather than on prose. `request()` accepts `{ signal }` for cancellation, which the message list relies on so that switching folders quickly cannot race a stale response into the UI. `requestBlob()` handles binary responses (attachments) and reads the file name from `Content-Disposition`. `mailAttachmentUrl()` builds the download URL so its encoding lives in one place. **Folder paths are always `encodeURIComponent`-encoded** — they may contain `/`, `&` or `#`.

## Auth

Session state is **cookie-based**, not a localStorage bearer token — `api.js` sends `credentials: 'include'` on every `fetch` and relies on the backend's `HttpOnly` cookie. `localStorage` only holds a non-secret `sessionActive` flag (`markLoggedIn()` / `clearSession()` / `hasSession()` in `api.js`) so the SPA can synchronously decide whether to attempt rendering an authenticated route before the first API round-trip; the flag carries no auth weight by itself; a stale flag with an expired/absent cookie just gets corrected by the first 401.

`AuthContext` (`src/contexts/AuthContext.tsx`) is the source of truth for the rest of the app:
- `isLoggedIn` — seeded from `hasSession()`, flipped by `syncFromSession()` and by the 401 handler.
- `syncFromSession()` — re-reads `hasSession()`; called by `LoginRoute` right after `LoginPage`'s `onLogin` fires (i.e. after `api.login()` succeeded and called `markLoggedIn()`).
- `logout()` — calls `api.logout()` (best-effort), then always `clearSession()` + `setIsLoggedIn(false)`.
- `account` / `accountLoaded` — populated by `refreshAccount()` (calls `api.getAccount()`), which runs automatically whenever `isLoggedIn` flips true.
- `identity` — `deriveIdentity(account)` or `null` before the account loads.
- `accounts` / `activeAccountId` / `activeAccount` / `accountsLoading` / `switchAccount` — **the multi-account state, no longer scaffolding**. `accounts` is the primary followed by every mailbox the user has attached (`GET /api/ConnectedAccounts`), each `{ id, email, displayName, isPrimary, domainName, credentialsValid, sieveSupported }`. **`activeAccountId` is the id, not the resolved account, and it is what every query key carries**: the id is read straight from `localStorage` at mount while the metadata needs a round trip, so keying on `activeAccount?.id` would send every mail query to the primary mailbox for the width of the accounts fetch and cache the answer under the wrong account. Readers that need the metadata wait on `accountsLoading` instead. `activeAccount` falls back to the primary **only once the list has landed** — during the load window it is `null`, for the same reason. An effect corrects a persisted id whose row came back `credentialsValid: false` or which the list no longer holds, so a stale `localStorage` value cannot strand the session on a mailbox nothing can open. `switchAccount` refuses a target with invalid credentials, and drops the outgoing account's `['mail', id]` queries on the way out so the next visit re-reads rather than showing the previous mailbox from cache.
- `isAdmin` — derived from `account?.isAdmin === true` (also mirrored into `api.js`'s module-level `isAdmin` flag via `setIsAdmin`; `api.js` exposes no public getter for it — the mirror is kept solely because `AuthContext` writes it, not because anything currently reads it back).

**401 handling** — `api.js`'s `request()` calls `clearSession()` and the registered `unauthorizedHandler` on any 401. `AuthContext` registers that handler on mount, setting `isLoggedIn = false` / clearing `account`. Since every authenticated route sits under `RequireAuth`, the next render redirects to `/login` — no page needs to know about auth internals.

**A session ending flushes every cache that outlives it**, in the one effect that reacts to `isLoggedIn` — `queryClient.resetQueries()`, `queryClient.getMutationCache().clear()` and `forgetNotificationClaim()`. The `QueryClient` is a module singleton, so nothing else empties it short of a page reload, and the query keys are account-scoped, but every account of one *session* is still another session's to inherit: without this, signing in as somebody else reads the previous user's folders, messages, contacts and preferences straight out of the cache under the identical `'primary'` key — the bug this fixes was exactly that, corrected by an F5 and nothing else. It lives on the `isLoggedIn` transition rather than inside `logout()` for two reasons: the 401 path (an expired cookie, then a sign-in as somebody else) is covered by the same line, and by the time the effect runs `RequireAuth` has already rendered `<Navigate>`, so the readers of what is being dropped are unmounted. **`resetQueries`, never `clear()`**: `clear()` *removes* every query, and a mounted observer whose query leaves the cache is never told — it keeps its last result and never sees another change. `RequireAuth` unmounts the authenticated readers, but `InstallManifest` sits above the router and outlives every session, so `clear()` left it observing a detached query and blind to `['appSettings']` for the rest of the tab: switching the app off no longer withdrew the manifest. `resetQueries` drops the data of every query while leaving them in the cache, and refetches the **active** ones only — the readers just unmounted are inactive, so nothing doomed is refetched, while the manifest's settings come back on their own. The mutation cache is the one thing `clear()` emptied that `resetQueries` does not, hence the second line. The notification claims need their own removal because `localStorage` outlives the tab, not just the cache. **There is one claim per account, not one claim** — `mail.lastNotifiedUidNext.<accountId>`, `CLAIM_PREFIX` in `notify/channels.ts` — because `uidValidity` is unique per mailbox and means nothing across two of them: under a single key, the account with the higher `uidNext` banks a value that gags the other's new-mail sound until its own `uidNext` climbs past it. `forgetNotificationClaim()` therefore sweeps **every key carrying the prefix** rather than removing one name, so ending a session clears the claims of all the accounts it touched.

## Theming

**A token names a role, never a color — components never hard-code a color**; add a role token if one doesn't exist. The full contract (the six palette files and their parity test, the pre-paint script in `index.html` that repeats `PALETTE_IDS`, the deliberate dark-mode hue-shifts that must not be "fixed") lives in `.claude/rules/frontend-theming.md`, loaded when working on `src/styles/`, `ThemeContext.tsx`, the Appearance page or `index.html`.

## Testing

Test files sit next to what they test (`Foo.tsx` → `Foo.test.tsx`, `Foo.jsx` → `Foo.test.jsx`), no separate `__tests__` tree. `src/test-setup.js` is the Vitest `setupFiles` entry (jest-dom matchers). Notes on specific suites:
- `src/api.test.js` — token/session management, all `api` methods, 401 handling.
- `src/modules/settings/aliases/AliasesPage.test.jsx` — alias CRUD, toasts, only the default export (see below).
- `src/modules/settings/rules/RulesPage.test.jsx` — `RuleCard`, `RuleEditorModal`, `ConvertConfirmModal`, the `isConditionValid`/`isActionValid` helpers, and the `RulesPage` default export.
- `src/modules/settings/admin/AdminPage.test.jsx` — `AdminPage`, `AccountsTab`, `DomainsTab`, `VirtualDomainsTab`, `AddEditUserModal`, `AddEditDomainModal`.
- `src/pages/LoginPage.test.jsx` — the login form. `src/pages/LoginRoute.tsx` (routing glue) has no dedicated test; it's exercised indirectly via navigation-flow tests.

**Named exports for tests — no longer a blanket rule.** The old convention ("every component under test carries a named `export` in addition to the default") is gone as a project-wide requirement. Shared, genuinely reusable pieces were extracted into their own files under `src/components/`/`src/hooks/`/`src/lib/` (Task 3) and are imported directly by whatever tests them — `AliasesPage.jsx` itself now has **only a default export** since its sub-components (`AccountPanel`, `ChangePasswordModal`, `QuotaBlock`, `Toasts`) were extracted or retired. Large page-local files that still bundle multiple sub-components in one module (`RulesPage.jsx`, the admin tab files) keep named exports alongside their default export purely so their tests can mount those sub-components in isolation — that's a per-file pragmatic choice now, not a house rule.

**No test lost without a replacement.** When moving/renaming a component (a `git mv`, an extraction, a retirement), the tests that covered its old behavior must keep covering it — either by moving with the file or by being folded into the destination's test file. A refactor that reduces the total assertion count on a behavior without an explicit reason is a regression, not a cleanup.

## Deployment

**Pushing deploys — there is no manual release step.** `.github/workflows/deploy.yml` runs on every push: it detects that `src/frontend/**` changed, runs this project's CI (lint, typecheck, tests, build), and only then uploads `dist/` over SSH into `/var/www/admin/mail/account.frontend`. The target environment follows the branch — `prod` on `master`, `dev` on anything else, so a push to a feature branch lands on `account-dev`.

The former `ship-frontend` skill and the local `npm run deploy` / `npm run ship` scripts are gone. The old script uploaded the **whole project** rather than `dist/`, and hard-coded one machine's absolute path — running it would have overwritten the docroot with source files. Deploy by pushing.
