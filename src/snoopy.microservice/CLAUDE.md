# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Projects

The backend is four projects under `src/`, in one solution (`src/snoopy.microservice.sln`):

- **`snoopy.microservice/`** — the core library (`snoopy.microservice.core.csproj`, assembly `snoopy.microservice.core`). Everything the webmail is, and nothing about the platform hosting it. **It never references the provider.**
- **`snoopy.microservice.host/`** — the composition root: `Program.cs`, `appsettings*.json`, `Properties/`. Assembly name stays `snoopy.microservice`, because the systemd unit and the release chmod name the executable. It is the only project that references both the core and a platform provider, and it picks one from `"Platform"`.
- **`snoopy.providers.weesky/`** — the weesky.net platform: the dovecot `ApplicationDbContext` and its entities, the users/aliases/admin repositories, `AdminController`, `AliasesController`, `AccountManagementController`, `DovecotQuotaClient`, `AdminRequirementHandler`, and the three `Platform` adapters. Namespaces are `weesky.Snoopy.Providers.Weesky.*`.
- **`snoopy.microservice.Tests/`** and **`snoopy.providers.weesky.Tests/`** — one suite per production project. The provider suite links four helpers out of the core suite's `Infrastructure/` rather than copying them.

The dependency direction is host → provider → core, and it is what makes the split real: were the core to reference the provider, "generic" would ship the dovecot code it claims not to have.

## Commands

```bash
cd src && dotnet build          # Builds the whole solution
cd src && dotnet test           # Runs both suites (always use this, NOT --no-build, when new test files have been added)
cd src/snoopy.microservice.host && dotnet run   # Run on localhost:5104 (opens Swagger UI)
```

Tests live in the two `*.Tests` projects (xUnit 2.9.3, Moq 4.20.72, EF Core InMemory). Repository tests use a per-test in-memory database via `TestDbContext`. Controller tests use `Moq` and `ControllerTestHelpers.CreateAuthenticatedContext`.

**`Platform` is also an MSBuild property name.** Setting it as an environment variable in front of `dotnet run`/`dotnet build` configures the *build*, not the app; put it in `appsettings.json` or `launchSettings.json`, or run the built binary directly.

**Pushing deploys — there is no manual release step.** `.github/workflows/deploy.yml` runs on every push: it detects that any backend project changed, runs the backend CI (one build and test pass over `src/`), and deploys over SSH only if CI passed. The target environment follows the branch — `prod` on `master`, `dev` on anything else. The former `ship-microservice` skill and its manual procedure are gone.

## Architecture

**weesky.mail.snoopy** is an ASP.NET Core (.NET 10) REST API for weesky.net mail administration. It manages email accounts, aliases, and domains backed by a Dovecot/MariaDB database.

### Layers

**Controllers** (`Controllers/`) receive HTTP requests and return `ResultEnveloppe<T>` responses via helpers in `ApiBaseController`. The main controllers are:
- `LoginController` — `POST /api/login` (issue JWT), `DELETE /api/login` (revoke cookie)
- `AccountController` — `GET /api/account` (info), `GET /api/account/quota` (the primary mailbox's quota, read live over IMAP GETQUOTAROOT INBOX rather than doveadm; 200 with the same `Quota` shape, 204 when the server does not advertise the QUOTA capability). The two writes that touch the platform's own directory — `PATCH /api/Account/ChangeSecret` and `POST /api/Account/FullName` — live in the provider's `AccountManagementController`, which carries an explicit `[Route("api/Account")]` for the same reason the four `api/Mail` controllers do: `[controller]` would move both URLs
- `AliasesController` — `GET/POST/DELETE /api/aliases` (alias CRUD, scoped to caller's owned domains)
- `AdminController` — admin-only CRUD (class-level `[Authorize(Policy = AdminRequirement.PolicyName)]`; non-admins get **403**, unauthenticated callers 401): users (`GET/POST/PUT/DELETE /api/Admin/users`, `GET /api/Admin/users/{id}/quota`), domains (`GET/POST/PUT/DELETE /api/Admin/domains`), virtual alias domains (`GET /api/Admin/domains/virtuals`, `PUT /api/Admin/domains/virtuals/{domainId}`, `DELETE /api/Admin/domains/virtuals/{domainId}/{userId}`)
- `RulesController` — Sieve mail-filtering rules: `GET/PUT/DELETE /api/Rules` (structured `SieveRule[]`), `GET/PUT /api/Rules/Raw` (unparsed script for Advanced scripts), `POST /api/Rules/CompatibilityCheck` (preview rules a target provider can't represent), `GET /api/Rules/Providers` (registered providers + default flag). See `DESIGN.md` and the repo-root `DESIGN-rules.md`.
- The four `api/Mail` controllers (`MailFoldersController`, `MailMessagesController`, `MailAttachmentsController`, `MailComposeController`, all on `MailControllerBase`) — IMAP access **on whichever mailbox the request names, not on the caller's own**. They share one route prefix, so each carries an explicit `[Route("api/Mail")]`: the `[controller]` token would give four classes four different prefixes and silently move every URL. `MailRouteSurfaceTests` pins the verb, template, status list and filter set of all 25 actions against exactly that. Every action begins with `TryResolveAsync`, which hands the `X-Account-Id` header (absent, or the literal `primary`, means the caller's own mailbox) to `IAccountConnectionResolver` and gets back one `MailAccountConnection` — host, port, transport security, username and password, whether the target is our own server or an admin-curated external domain. Nothing in this controller reads `MailOptions`, and no method takes a bare username any more: the connection travels as one argument, so an action physically cannot address the wrong mailbox by forgetting a parameter. Three of the four statuses in rule 4 (401, 404, 409) are produced by that resolution, **before** the action's own logic runs, and the per-endpoint statuses listed below are what each answers once it has succeeded. Staged attachments are namespaced per user *and* account (`MailAccountConnection.StagedScope`), so an id staged while reading one mailbox is invisible from another. The endpoints: `GET /api/Mail/Folders` (tree with roles, subscription state, counts, `UidValidity`), `POST/PUT/DELETE /api/Mail/Folders` (create / rename / delete), `PUT /api/Mail/Folders/Subscription` (visibility), `GET/PUT/DELETE /api/Mail/FolderRoles` (affectation des rôles systèmes — chaîne surcharge utilisateur → SPECIAL-USE → nom), `GET /api/Mail/Messages?folder=&page=&pageSize=` (page of envelopes, newest first, page size capped at 200), `GET /api/Mail/Messages/Detail?folder=&uid=` (sanitised body + attachment list), `GET /api/Mail/Messages/Attachment?folder=&uid=&part=` (binary, always an attachment disposition), `PUT /api/Mail/Messages/Flags` (sets or clears `seen`/`flagged` on a batch of up to 200 UIDs; a UID the folder no longer holds is a silent no-op, so the batch never half-fails), `POST /api/Mail/Messages/Move` / `POST /api/Mail/Messages/Copy` (body `{ folderPath, uids, targetFolderPath }`), `DELETE /api/Mail/Messages` (body `{ folderPath, uids }`, permanent expunge — `\Deleted` + `UID EXPUNGE` — the caller is expected to move to trash instead for an everyday delete), `POST /api/Mail/Folders/Empty` (body `{ folderPath, targetFolderPath? }`, purging with 1:* `\Deleted` + a bare `EXPUNGE` when no target is given, moving every message to the target otherwise; 204/400/401/502), and `POST /api/Mail/Messages/Search` (criteria combine with AND, `Quick` means subject OR sender, `AllFolders` sweeps every selectable folder in one IMAP session, `HasAttachment` has no standard IMAP SEARCH criterion so it is post-filtered on `BODYSTRUCTURE` before pagination; 200/400/401/502), `POST /api/Mail/Attachments` (multipart upload; stages one outgoing attachment under the caller's account, no IMAP session involved; an `inline` flag stages it as a body resource rather than an attachment, assigning it a Content-ID and refusing a non-image with 400; 200 with the staged id + metadata, 400 for no file / a non-image staged inline / over the size limit / the account's staging cap reached, 401), `DELETE /api/Mail/Attachments/{id}` (removes a staged attachment; **204 whether or not it existed**, including for an unknown id or one staged by another account — the staged namespace is sealed per user *and* account, so a foreign id resolves to nothing and a 404 would leak its existence. That 204 is the answer to the **deletion**, no longer to the request as a whole: account resolution runs first, so the call answers 401, 404 or 409 whenever the resolution itself fails, exactly as every other action here does), and `POST /api/Mail/Send` (body `{ to, cc, bcc, subject, htmlBody, attachmentIds, fromAddress? }`; an omitted `fromAddress` sends as the primary — the pre-2c2a behaviour — while a present one must name the primary or one of the account's **live** aliases, checked before any SMTP session opens, with the display label always resolved server-side from the stored identity, never taken from the request; sends over SMTP then best-effort APPENDs a `\Seen` copy to the Sent folder — **200** with `{ appendedToSent }` in every case, `appendedToSent: false` when only the Sent copy failed to file, since filing it never fails the request; 400 for no recipient / an invalid address / a `fromAddress` the account does not own / an unknown staged attachment id, 401 for no credentials cookie, 502 when the mail server refuses the submission), `POST /api/Mail/Messages/PrepareQuote` (body `{ folder, uid, purpose: "reply"|"forward"|"editAsNew" }`; outbound-sanitised quotable body with cid images rewritten to staged URLs, inline parts staged, forward/editAsNew re-stage the real attachments server-side; 200/400/401/404/502), `GET /api/Mail/Attachments/{id}/content` (serves a staged file to its owner for the composer's inline images, attachment disposition + nosniff; 200/401/404), `POST /api/Mail/Drafts` (body `{ to, cc, bcc, subject, htmlBody, attachmentIds, fromAddress?, replaceUid? }`; the same validation Send runs minus the recipient gate, so an empty or recipient-less draft is valid; APPENDs `\Draft \Seen` to the drafts-role folder and, when `replaceUid` names one, expunges the previous version best-effort/non-fatal — the staged attachment files are left for the still-open composer; 200 with `{ uid, folderPath }`, 400 for an invalid address / a `fromAddress` the account does not own / an unknown staged attachment id, 401, 502 when no folder holds the drafts role or the mail server refuses the save), and `POST /api/Mail/Drafts/Open` (body `{ folder, uid }`; reuses PrepareQuote's EditAsNew pipeline — envelope, editable body, the draft's real attachments re-staged under the calling account, `inReplyTo`/`references` carried through for the composer seed; 200/400/401/404/502). The write endpoints (Move / Copy / Delete / Empty) answer 204 on success, 400/401/502 otherwise; Search answers 200 with the results page; and the delete refuses outright when the session lacks IMAP UIDPLUS
- `IdentitiesController` — the curated From list, a webmail preference stored in `snoopy_webmail`, not mail-server data (no IMAP session, no credentials cookie): `GET /api/Identities` (the resolved list — the primary address always present, then every stored row, sorted default-first then by label, each carrying `address`/`displayName`/`isDefault`/`isPrimary`/`stale`/`labelIsCustom`), `PUT /api/Identities` (replaces the whole set atomically; 204, or 400 naming the offending address — an address must be the primary, a live alias, or already stored, so a row survives being left untouched across a save even after its alias is gone)
- `ContactsController` — the user's address book, webmail data like the identities above (no IMAP session, no credentials cookie, everything scoped by the caller's `WebmailUid`): `GET /api/Contacts` (the whole book in one answer — searching and sorting are the client's job over that cached list, which is also why `ContactStore` caps a user at 5000 contacts and `ContactValidator` a contact at 50 addresses: the ceilings bound the payload as much as the table), `POST /api/Contacts` (200 with the created contact, **answered from the validated write rather than re-read**, so the caller gets the canonicalised, deduplicated address list the store actually holds instead of its own spelling; 400 for neither name nor address, an unparsable address, or the cap reached), `PUT /api/Contacts/{id}` (replaces the contact whole — names, favourite flag and the entire address list; 204/400/404), `DELETE /api/Contacts/{id}` (204/404), and `PUT /api/Contacts/{id}/Favorite` (204/400/404). Two rules read badly from the code alone. **A contact belonging to another user answers 404, never 403**: the store's `FindAsync` is scoped by user, so a foreign id resolves to nothing at all and the controller has no other status to give — 403 would confirm the id exists, which is the leak the scoping exists to prevent, and it is the same choice `DELETE /api/Mail/Attachments/{id}` makes for the staged namespace. **The favourite has a route of its own** because the star is toggled from a tile holding a possibly stale copy: a whole-contact `PUT` from there would clobber an edit made meanwhile, exactly why message flags are not sent as a whole message either. `POST /api/Contacts/Import` (multipart, capped at 20 MB by `[RequestSizeLimit]` so the read is bounded before `IFormFile` buffers it; it takes a **CSV or a `.vcf`**, told apart by media type then by content) and `GET /api/Contacts/Export` (`text/csv`, one attachment) are the import/export pair. **The import merges on the address, or failing that on the exact name, and overwrites nothing**: a row whose address is already known to exactly one contact fills that contact's empty fields and appends its unknown addresses, one known to several contacts is skipped as ambiguous — the question slice 3a left open, answered by refusing to pick — and anything else is created with `source = "imported"`. A row carrying **no** valid address falls back to a second index, the normalised name triple → contacts, which holds **only contacts that have no addresses at all**: the exporter always writes the addresses a contact has, so a name-only row can only ever be describing an address-less one, and without that fallback re-importing our own export created one duplicate per address-less contact on every replay. A row that has an address never consults it — the address is the stronger signal — and a name on two address-less contacts skips the row with a reason of its own, since saying "address" in front of a row that carries none is unreadable. The name normalisation is deliberately **not** `IdentityResolver.Canonical`: that one folds addresses. It is one `SaveChanges` for the whole file. **"Empty fields" means all of them, not just the names**: the merge fills middle name, prefix, suffix, display name, org, department, job title, birthday, URL and notes wherever the target holds none, and poses the incoming phones or postal addresses **all-or-nothing** — a target holding one phone is handed none, because two spellings of the same number cannot be told apart without a normalisation neither `TEL` nor `ADR` has. Both readers feed it through `ContactImportRow.Write`, so a `.vcf` and a CSV row offer the same thing. The decision rests on `ContactStore.Holdings`, kept current across the rows of one file rather than read off the columns, which are written once at the very end — read off the columns, a second row aimed at the same target would see it empty and double the family it just posed, and a target *born* of the same file would have its own card's `ORG` overwritten. The photo is the one thing a merge still does not carry: it arrives with a verbatim card at creation, and the composer has no `PHOTO` write door (décision 12). **Columns we do not model do not vanish**: a CSV row's phones, org, postal addresses, notes, birthday and URL travel through `VCardComposer` into the vCard 3.0 stored in `vcard_raw` — the card every contact now has, and the one the columns are projected from. A `.vcf` card is stored **verbatim, byte for byte**, never re-serialised, to within a single line: a card declaring no `UID` gets one equal to its `uid` column inserted after `VERSION`, textually, at the one place `vcard_raw` is written, because every stored card must carry the identity a CardDAV client syncs on and synthesising it when serving would divorce the bytes served from the bytes hashed. The export writes the primary address in `E-mail Address` — the column Rainloop and Outlook read — and the rest in `E-mail N Address`, which only we read back; the round trip through our own file is a tested claim. **A name that a spreadsheet would evaluate goes out behind an apostrophe** and the mapper strips exactly one back off, names only — the apostrophe is in the trigger set itself so the pair is symmetric, and the guard lives in `ContactCsvExporter` rather than in `CsvWriter`, which is a general CSV primitive. A **CSV round trip does not carry `vcard_raw` back out**, since re-emitting it needs the vCard reader of the next slice.

**Repositories** (`Repositories/`) handle all database access via EF Core. `UsersRepository` no longer validates credentials — login is an IMAP LOGIN attempt, judged by the mail server itself — it only looks up account info and updates passwords; `AliasesRepository` lists/creates/deletes aliases and enforces domain ownership via the `MailDomainOwnership` join table. `SendingIdentityStore` (behind `ISendingIdentityStore`) reads and whole-set-replaces `sending_identities` in the separate `snoopy_webmail` preferences database (`PreferencesDbContext`) — it does no validation of its own, that is `IdentityResolver`'s job, run by the controller before the store is ever called. `ContactStore` (behind `IContactStore`) lives in the same preferences database and follows the same division — `ContactValidator` is its `IdentityResolver`, a pure static class run by the controller so `POST` and `PUT` read one rule rather than two that could drift. `SieveRepository` (behind `ISieveRepository`) is the exception — it does **not** use EF Core; it reads/writes Sieve scripts over ManageSieve (`IManageSieveClient`), detecting/compiling/parsing them through the `RuleProviders`.

**Services** (`Services/`) wrap external integrations. `DovecotQuotaClient` (typed `HttpClient`) calls the remote doveadm HTTP API (`quotaGet`) to retrieve live mailbox quota. `ManageSieveClient` (behind `IManageSieveClient`) opens authenticated ManageSieve sessions (RFC 5804, port 4190, SASL PLAIN with the account's own credentials, never a master user) exposing list/get/put/setactive/delete script verbs. `ImapConnectionFactory` opens one MailKit `ImapClient` per request and hands it to an `ImapSession`; `MailCredentialStore` encrypts the user's mail password into a cookie; `MailHtmlSanitizer` makes message bodies safe to render. `IdentityResolver` is the odd one out — a pure static class, no external call at all — kept here anyway because it is a service in the ordinary sense: the single place the sending-identity rules (canonicalisation, ownership, the merged list, validation) are written, so `IdentitiesController` and `MailSender` read the same rule instead of two that could drift apart.

### Mail — the eight rules a newcomer would otherwise breach

1. **Nothing about the mail server is configured.** `MailOptions` holds connection parameters only (host, port, `SecureSocketOptions`, timeout). The hierarchy separator, namespace, special-use folders and capabilities are all read from the live IMAP session, with a name-based fallback where the server advertises no `SPECIAL-USE`. That fallback resolves **across the whole folder list, not folder by folder** (`ResolveSpecialUses`): a mailbox provisioned by two clients holds both `Drafts` and `Brouillons`, and each role must land on exactly one folder. Server flags are claimed in a first pass and name guesses only fill roles still unclaimed, so a guess can never overrule what the server actually said. This is what will let a later slice point at arbitrary external servers whose configuration we will never hold — code that hard-codes a server fact is wrong even when it works today. `MailOptions` is consumed through **`IOptionsMonitor`**, not `IOptions`, so connection values can be corrected in `appsettings.json` without restarting and dropping live sessions.
2. **Message order comes from the server, not from sequence numbers.** `ListMessagesAsync` asks for `SORT (REVERSE DATE)` when the session advertises `SORT`, and pages the returned UID list; without the capability it falls back to a window on the sequence numbers. Sequence order is arrival-*into-the-folder* order — identical to date order in an inbox, but not in a folder messages are moved to, where a trash listed by when each message was thrown away. **The capability list must be read after authentication**: Dovecot advertises a much shorter one before login, and `SORT` is absent from it. A `UID FETCH` may answer in any order, so the summaries are re-ordered to the sorted list (`InOrderOf`).
3. **Folder paths never appear in a route segment.** The separator may be `/`. They travel in the query string (GET) or the request body (POST/PUT/DELETE). Responses carry `UidValidity` so a client can tell when its cached UIDs went stale.
4. **Four distinct failure modes, and the one that must not be collapsed is 409 into 401.** A missing or undecryptable *credentials cookie* is **401** carrying `credentials_unavailable`, so the client signs in again rather than showing an opaque IMAP error. A request naming an account the caller does not hold is **404** carrying `account_not_found` — an unparseable id, an unknown id, another user's id and a domain row whose stored transport security no longer parses are all deliberately indistinguishable, since telling them apart would say whether an id exists. A *connected* account whose stored cipher no longer decrypts under the session key is **409** carrying `connected_credentials_invalid`: the main password was changed outside the app, so one attached mailbox needs its password re-entered while the session itself is entirely valid — this is why it may never be spelled 401, which the frontend's global handler reads as "sign out", ejecting the user from the whole webmail over one mailbox they may not even be reading. Anything the mail server refuses is **502**. The two constants live in `ConnectedAccountErrors` and the mapping in `ApiBaseController.ConnectedAccountError`, the single place all three are produced — reached from the mail controllers and `RulesController` through `MailControllerBase.TryResolveAsync`, which answers an `AccountResolution<T>` whose `Failed` accessor makes the compiler prove the non-null branch, and directly from `IdentitiesController`, which resolves no connection of its own. `ImapSession.MessageNotFound` / `.AttachmentNotFound` are shared constants of the same kind — not literals repeated in the controller — mapped to **404** as well, so the layer producing an error and the layer choosing a status cannot drift apart; they share that status with an unknown account only because both describe a thing that is not there, never because they travel the same path.
5. **Folder roles resolve through an ordered chain, and its output is what the client sees.** User override (per account, stored in the separate `snoopy_webmail` database via `PreferencesDbContext`/`IFolderRoleStore`) → `SPECIAL-USE` flags → multilingual name fallback, each level filling only what the previous left, tracking **both** claimed roles and claimed folders — one folder never holds two roles. `FolderRoleResolver` is pure over the tree and the stored rows; `GET /Folders` stamps its `RoleByPath` onto every node's `SpecialUse`. Overrides store the **path** (the only identifier IMAP guarantees), guarded by `uid_validity` against path reuse, with RFC 8474 `MAILBOXID` as an optional aid — never the key. Stale overrides are kept and signalled, never auto-deleted. Our own renames/deletes move or purge the rows (IMAP first, database second; a failed bookkeeping write degrades, never fails the user's operation). Database creation is manual — see `docs/superpowers/mail-2a5-database-prerequisite.md`; the service refuses to start without the `WebmailPreferencesDatabase` connection string.
6. **The sanitiser's allowlists are a policy over Ganss/AngleSharp, and three of their rules are load-bearing.** *(a)* **A shorthand must carry its longhands, or it drops too.** The parser expands `border-top` into `border-top-width/style/color` and `text-decoration` into `-line/-style/-color` **before** the name allowlist runs, so allowing only the shorthand silently erases the declaration. This has bitten three times — hairline rules, button underlines, rounded corners. *(b)* **An unknown tag is unwrapped, not deleted with its subtree** (`UnwrapDisallowedTags`), because one bpost mail wrapped its whole 62 KB body in a single `<center>`. Only `DropWithContent` — script, style, svg, math, template… — takes its content with it; that list is DOMPurify's `FORBID_CONTENTS` boundary and must not be widened casually. *(c)* **A CSS `url()` is judged by the property it sits on and by its scheme, and only `background-image` earns a way back.** A remote layer of a `background-image` is *withheld* rather than culled — moved out of the CSS into `data-blocked-bg` on the element and counted into `blockedImageCount`, exactly as an `<img src>` is moved into `data-blocked-src` — so the banner can offer it and the reader can restore it through CSSOM on consent. Only `http`/`https` are withheld: a `url(cid:…)` layer stays in the CSS untouched, because its bytes never leave the mailbox and the client resolves it into a data URI, and a layer of any other scheme is dropped outright — nothing to restore is nothing to validate later. **Every other property is still culled by value**: a `url(` in `border-image` or `list-style-image` takes its whole declaration with it, since there is no consent surface for it and it would fetch on render. **A declaration carrying a backslash is culled outright**, wherever it sits — `\75 rl(` is the same fetch spelled past a naive reader — and that cull runs in a **pre-Ganss pass on the raw attribute** (`CullEscapedDeclarations`), because AngleSharp resolves the escape while parsing and the second pass would only ever see `url(` spelled plainly. The withholding is what makes the whole image-blocking model hold for CSS as well as for `<img>`; reinstating a blanket cull would silently break restoration, and widening it past `background-image`, past http/https, or past the pre-Ganss escape pass would put a fetchable URL in the rendered body without consent. Note also that neither `data-blocked-src` nor `data-blocked-bg` is in `AllowedAttributes`: both are written by our own post-Ganss pass, and a message allowed to bring its own would load on consent without ever being counted, understating what the banner promises against what it actually grants. Widening the CSS allowlist is routine; touching these three is not.
7. **Only the topmost `Authentication-Results` header is trusted, never merged with the ones below** (`MailAuthenticationReader`). A message accumulates one such header per relay it crosses, prepended, so the top one is what our own receiving server wrote and every header beneath it was written by an untrusted upstream — or forged by the sender, who can put `Authentication-Results: spf=pass` in anything they send. A verdict missing from the top header stays `null`; borrowing it from a lower header would reopen a spoofing vector. Parsing is delegated to `MimeKit.Cryptography.AuthenticationResults` (a hand-rolled `;`-split misread RFC 5322 comments and leaked a `)` into a verdict); within that one header a method repeated for two DKIM signatures passes if **any** occurrence passed. The backend only reports the verdicts — green/red/nothing is a frontend display rule, so this layer never decides trust, it transcribes it. **`Received` is the one documented exception, and it is the rule applied correctly rather than an entorse** (`MailHeaderDetailsReader.BoundaryReceived`): our own server writes *two* of them — Postfix at the network ingress, then Dovecot's LMTP handoff prepended on top — so our trusted zone spans more than one occurrence, unlike every other header here. Reading the topmost reported "no encryption" on every delivered message, because a local socket carries no TLS. The reader therefore skips the local-delivery dialects (`LMTP*`, Postfix's `local`) and stops at the first network hop; it must **stop** there rather than hunt the chain for a TLS mention, or a forged `Received` deeper down would light the padlock. `MailSpamScoreReader` obeys the same rule for the anti-spam headers (`X-Spamd-Result`, `X-Spam-Status`/`X-Spam-Score`, `X-MS-Exchange-Organization-SCL`): topmost occurrence of each name, rspamd first because it is the filter this platform itself runs, and an unreadable header moves to the next engine, never to a lower occurrence. The thresholds mean different things per engine — rspamd's is its reject line (~15), SpamAssassin's its flag line (5) — so the frontend's score/threshold ratio is comparable within one engine, not across engines; the printed numbers and the raw header in the tooltip are what stay honest either way.
8. **The sending-identity list merges three sources into one, and `IdentityResolver` is the only place that merge is written.** `Resolve` puts the primary address first (labelled from a stored row, then the account's `FullName`, then the address itself), then every stored `sending_identities` row; a stored row whose address the account no longer owns among its live aliases comes back `Stale` — kept and flagged, never dropped, the same "signal, don't delete" choice rule 5 makes for a folder-role override on path reuse. Ownership (`Owns`/`OwnsCanonical`) is judged solely against the **live** alias list, never the stored table, so a stale row cannot hold the default either — with none of the live rows marked default, the primary is the default, resolved at read time and never persisted. `Validate` (called by `PUT /api/Identities`, never by the store itself) accepts {primary} ∪ {live aliases} ∪ {already-stored addresses}: the third branch is what lets a save that does not touch a stale row keep it alive, while a brand-new address the account never owned is still refused.

**Sending reuses the same credentials cookie, but talks to SMTP, not IMAP.** `MailSender.SendAsync` retrieves the caller's mail password from the same cookie `MailCredentialStore` reads for every other mail action, then opens it through `SmtpConnectionFactory`. The outgoing sanitizer (`OutgoingMailSanitizer`) is a **different** allowlist from the display one in rule 6 above — it prepares a compose body for delivery, not an inbound body for display, and the two must not be conflated. Staged attachments (`IStagedAttachmentStore`) are namespaced per account: an id staged by one account is invisible, not merely denied, to another. Bcc recipients are envelope-only on the wire — MailKit strips the header at transmission, so only the addressees see it went out — but the header is kept on the copy filed to Sent, so the sender can still see who was blind-copied. **SMTP auth always uses the account's own credentials — only the header and envelope From change** when `fromAddress` names an alias, which requires Postfix's `smtpd_sender_login_maps` to authorize that alias for the authenticated user; when the server refuses the sender, `SmtpSession.DescribeFailure` names the address in the error (`SmtpErrorCode.SenderNotAccepted`) rather than surfacing a bare "message refused", since with alias identities the likely cause is that server-side map, not a malformed message.

**Authentication to IMAP uses the user's own password**, captured at login (it is unrecoverable from the database — MariaDB stores SHA-512 crypt) and kept in a Data-Protection-encrypted cookie. This is the Rainloop/Snappymail model, and the only one that generalises to external servers; a master user was considered and rejected because it works solely on the home server and would require a second authentication path. **The key ring must be persisted** — see `docs/superpowers/mail-2a-server-prerequisite.md`; without `StateDirectory=` in the systemd unit the service refuses to start outside Development.

**`TokenConstants.ExpiryInMinutes` is an *inactivity* window, not a session cap.** `SlidingSessionMiddleware` reissues **both** cookies — the JWT and the credentials one, together or not at all — on any authenticated request once less than half the lifetime remains, so an active session never expires under the user. What the value really buys is tolerance to silence: at 2880 (48 h) a session survives **at least 24 h and at most 48 h** without a single request, the spread being where in the half-life the last renewal fell. It was raised from 30 minutes because the webmail stops polling when its tab loses focus and notifications are off (`refetchIntervalInBackground` in the frontend's `queries.ts`), and a sleeping laptop sends nothing at all — half an hour of either signed the user out. The tests fix their own lifetime in their fixtures, so they assert the renewal behaviour and are indifferent to this value.

**RuleProviders** (`RuleProviders/`) compile/parse the shared `SieveRule[]` model to/from on-disk Sieve. `WeeskyRuleProvider` is the native superset (everything); `RainloopRuleProvider` is the Snappymail-interop format with a strict `CanRepresent` whitelist. `RuleProviderRegistry` holds them: `Default`=`weesky` (compilation fallback), `NewAccountDefault`=`rainloop` (new mailboxes are visible in the Snappymail webmail), plus `GetById`/`Detect`.

**Authentication** (`Authentication/`) configures JWT bearer + HTTP-only cookie auth. `UserAuthenticator` validates credentials by attempting an IMAP LOGIN with them — there is no local password check; `TokenManager` + `TokenBuilder` issue signed JWTs. Token constants (issuer, audience, expiry, signing key, cookie name) come from `appsettings.json` under the `"Token"` key. Admin endpoints use the `"Admin"` authorization policy (`Authentication/Authorization/`): `AdminRequirementHandler` resolves the Upn/Dns claims and checks `IAdminRepository.IsAdminAsync` per request.

**Data** (`Data/`) in the core holds only `Data/Preferences/` — the `snoopy_webmail` schema. The Dovecot schema (`ApplicationDbContext`, `MailUser`, `MailDomain`, `MailAlias`, `MailDomainOwnership`, `LastLogin`) belongs to the weesky provider.

### The platform seam

Three ports in `Platform/` are the whole of what the core knows about the directory behind a mailbox: `IAliasDirectory` (which addresses the account owns, and whether ownership is enforced at all), `IProfileReader` (its display name), `IAccountInfoProvider` (the account itself, and whether the platform still holds it as usable — what `SessionGuard` re-checks a live session against). `Platform/Generic/` answers all three from the token alone; the weesky adapters read the dovecot database.

`Program.cs` reads the root `"Platform"` key — `weesky` or `generic`, required, no default — through `IConfiguration.UsesWeeskyPlatform()`. In weesky mode it calls `AddWeeskyPlatform(configuration)` **and** `AddApplicationPart(typeof(WeeskyPlatform).Assembly)`; without the second, the platform's controllers would not be routes and a generic deployment would answer 500 out of a database it does not have instead of 404 out of a route it does not serve.

**That switch only decides anything because the host csproj sets `GenerateMvcApplicationPartsAssemblyAttributes=false`.** Left at its default, the Web SDK stamps `[assembly: ApplicationPart("snoopy.providers.weesky")]` onto the host, `ApplicationPartManager.PopulateDefaultParts` loads it, and MVC publishes every weesky route on both platforms — `api/Admin` answering 403 instead of 404, `api/aliases` 500, Swagger documenting endpoints the deployment cannot serve. With the attributes off, the host's *own* assembly is the only default part, so `Program.cs` must name the core part explicitly too (`AddApplicationPart(typeof(ApiBaseController).Assembly)`) or the webmail's controllers disappear as well. `PlatformRouteSurfaceTests` reads the real host assembly's attributes rather than a hand-written list, so re-enabling the property fails the suite.

Two consequences worth knowing before touching either side. The `Admin` **policy is declared by the core and its handler is not**: `AdminRequirementHandler` ships with the weesky platform, so on any other platform the policy is unsatisfiable — deliberate, and harmless because the two core routes that carry it are operator gestures a deployment holding no admin directory has nobody to run: `PUT /api/AppSettings` and `POST /api/Contacts/Backfill`. The latter is slice 4a's one-shot sweep — it gives a card, a hash and a projection to every contact stored before the vCard model existed (see `docs/superpowers/contacts-4a-backfill.md`), and only a deployment predating that slice has anything to convert. And the **health check is split**: the core probes `PreferencesDbContext` under the name `database`, the provider probes `ApplicationDbContext` under `weesky-database`; `/health` still emits only the aggregate, so each description names its own database.

### Key Patterns

- **Functional error handling:** Repository and service methods return `Result<T>` / `Result` from `CSharpFunctionalExtensions`. Controllers unwrap these and call `Ok(result)` / `Problem(result)` helpers from `ApiBaseController`.
- **JWT claims:** `ClaimTypes.Upn` = username, `ClaimTypes.Dns` = domain **name** (e.g. `"weesky.be"`, NOT the 3-char domain ID). `AdminRepository.IsAdminAsync` resolves name → ID via the `Domains` table before querying users. All EF repository methods are async (`Async` suffix, `Task<T>` return types).
- **Password storage — CRITICAL:** The microservice **must store passwords as plaintext**. MariaDB triggers `INSERT_PASSWORD` and `UPDATE_PASSWORD` on the `users` table automatically encrypt the value using SHA-512 crypt (`$6$...`) before it is persisted. Any server-side hashing (e.g. CryptSharp) would double-encrypt and break login. Always assign `Password = request.Password` directly — never hash.
- **Database:** MySQL via Pomelo EF Core provider. The `snoopy_webmail` connection string is `ConnectionStrings:WebmailPreferencesDatabase` at the root; the `dovecot` one is `Weesky:ConnectionStrings:MailUserAccountsDatabase`, read only under `Platform: weesky`. **The root-level `ConnectionStrings:MailUserAccountsDatabase` and the root `Dovecot` section are no longer read** — a deployment carrying them must move them under `Weesky` (environment variables `Weesky__ConnectionStrings__MailUserAccountsDatabase`, `Weesky__Dovecot__ApiKey`) and set `Platform=weesky`. The whole `Weesky` block is required on that platform and fails fast naming the key it is missing: the connection string throws out of `AddWeeskyPlatform`, `Weesky:Dovecot:ApiUrl`/`:ApiKey` through `ValidateOnStart`.
- **Assert.IsType&lt;T&gt; in tests:** Checks the **exact** runtime type. `BadRequest(body)` returns `BadRequestObjectResult` (a subtype of `ObjectResult`); always use `Assert.IsType<BadRequestObjectResult>` for those. Only `StatusCode(400)` / the `FromResult()` helper returns a plain `ObjectResult`.


## C# Coding Style

### File Organization

- **File-scoped namespaces always.** Block-scoped namespaces waste indentation for zero benefit.
- **One type per file.** File name must match the type name exactly (`OrderService.cs` contains `OrderService`).
- **Order members:** constants, fields, constructors, properties, public methods, private methods. Consistent ordering reduces cognitive load when scanning a file.

### Type Declarations

- **Primary constructors for DI injection.** Eliminates boilerplate field assignments and `_field = field` ceremony.

```csharp
// DO
public sealed class OrderService(IDbContext db, TimeProvider clock) { }

// DON'T
public class OrderService
{
    private readonly IDbContext _db;
    public OrderService(IDbContext db) { _db = db; }
}
```

- **Records for DTOs and value objects.** Immutability, value equality, and `with` expressions for free.

```csharp
public sealed record CreateOrderRequest(string ProductId, int Quantity);
public sealed record Money(decimal Amount, string Currency);
```

- **`sealed` on classes not designed for inheritance.** The JIT can devirtualize calls on sealed types, and it communicates intent clearly.
- **`internal` by default, `public` only when needed.** Minimize the public API surface. If nothing outside the project references it, it should be `internal`.

### Expressions and Patterns

- **Collection expressions over constructor calls.** Shorter, compiler-optimized, and consistent across collection types.

```csharp
// DO
List<int> ids = [1, 2, 3];
int[] arr = [4, 5, 6];

// DON'T
var ids = new List<int> { 1, 2, 3 };
```

- **Pattern matching over if-else chains.** Switch expressions and `is` patterns are more readable and exhaustiveness-checked.

```csharp
// DO
var label = status switch
{
    OrderStatus.Pending => "Awaiting payment",
    OrderStatus.Shipped => "On the way",
    _ => "Unknown"
};

// DON'T
string label;
if (status == OrderStatus.Pending) label = "Awaiting payment";
else if (status == OrderStatus.Shipped) label = "On the way";
else label = "Unknown";
```

### Naming and Modifiers

- **`var` for obvious types, explicit types when clarity matters.** Use `var` when the right-hand side makes the type self-evident (`var order = new Order()`); spell it out when it does not (`HttpResponseMessage response = await ...`).
- **Async suffix on all async methods.** `GetOrderAsync`, not `GetOrder`, for methods returning `Task` or `ValueTask`. Prevents accidental sync calls.
- **PascalCase** for public members, types, namespaces, and methods. **camelCase** for local variables and parameters.
- **No `_` prefix on private fields when using primary constructors.** The parameter name is the field name.


### Other rules
- Don't hesitate to use extensions methods
- Use **clean architecture**
- **ALWAYS** Prefer record types for immutable data structures.
- **ALWAYS** use ILogger with Structured logging to log, no string interpolation and no other logging methods.
- Serilog writes two daily files (HTTP requests apart from the rest) at `Information`. Two categories are turned down in `Program.cs` and must stay down: `Microsoft.AspNetCore`, and `Microsoft.EntityFrameworkCore.Database.Command` — the latter logs **every executed statement** at `Information` and buried the log under SQL. `Warning` still surfaces command failures, which EF logs at `Error` under that same category.
- **ALWAYS** use cancellation tokens for asynchronous methods.
- **ALWAYS** use Data Transfer Objects (DTO) for API communication, validated with attributes.
- **NEVER** use try-catch blocks solely to log and rethrow exceptions.
