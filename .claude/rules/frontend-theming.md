# Theming

Token contract lives in `src/styles/`:
- `tokens.css` — role tokens only (`--font`, `--radius-sm`, `--radius-md`, ...). **A token names a role, never a color.** Components must never hard-code a color; add a role token instead if one doesn't exist.
- `theme-<id>.css` — one file per **palette** (`night`, `classic`, `forest`, `slate`, `plum`, `ink`, `azure`, `indigo`), each defining the 39 role tokens for `[data-palette='<id>']` — 37 in the dark block, which inherits the two `--icon-hover-*` — further overridden by `[data-palette='<id>'][data-theme='dark']`. Sixteen combinations. `azure` and `indigo` were generated from one OKLCH seed each (chrome hue/chroma, neutrals temperature, an accent per mode) and then frozen to hex to match the older six; the seeds are not kept, the hex is the source. **Their dark accents sit near OKLCH L 0.70 on purpose**: white is the foreground over the accent (see below), and past ~0.72 white text falls under what the shipped `night` coral already spends. Four more shipped alongside them and were withdrawn on look — `olive`, `jade`, `graphite`, `harbor`. A stored preference naming one of them is not a migration problem: `paletteOf` and the pre-paint script both fall back to `night` for any id they do not recognise. **The selectors are deliberately not anchored to `html`**: an attribute selector matches any element, which is what lets the Appearance page's thumbnails re-declare a whole palette on one `<span>` and preview a palette that is not the active one. Anchoring them to `html[data-palette='…']` would blank every thumbnail while leaving the app itself correct. `src/styles/palettes.test.ts` asserts every palette file declares the same role set as `theme-night.css`, in both blocks — a missing `--quote-text` is a browser default nobody notices in review, and a missing `--list-row-selected-bg` silently falls back to the light value in dark mode.
- `shell.css` — application shell layout (topbar, rail, settings pane, etc.), consumes the role tokens.
- `contacts.css` — the contacts module: scope band, tiles, card and editor, plus its own touch and phone rules. Imported right after `index.css`, whose tail it used to be.
- `mail.css` — the mail module's three columns, folder tree, list rows and reader. New CSS goes here rather than into `index.css`, which is still ~2150 lines of shared rules. Carries no literal colour except inside a **`box-shadow`** — a shadow is a shading of whatever sits under it rather than a colour of its own and so has no role to name (the overlay scrim reads `--scrim`). Grep the file for `box-shadow` for the current set rather than trusting a count here, since one gets added or dropped without this note being told; as of writing there are four (`.drag-pill`, `.compose-tool:hover`, `.compose-popover`, `.floating-action`), and they are not even spelled alike — two write the newer space-separated `rgb(0 0 0 / alpha)` form and two write comma-separated `rgba()`, and `.drag-pill`'s is tinted (`rgba(10, 15, 30, 0.35)`) rather than grey. Copy the precedented `rgba(0, 0, 0, …)` form every other file in `src/styles/` writes when adding a new one — not `.drag-pill`'s tint, and not the `rgb(0 0 0 / …)` spelling.

Status roles: `--warning` (the quota bar's amber, darker in light mode so the fill keeps 3:1 against its `--border` track), `--status-fg` (text or a glyph over a filled `--danger`/`--success`: white in light mode, the palette's own dark ground in dark mode, whose status colours are light — `classic`'s a shade darker than its ground, which is 4.2:1 on `--danger-hover`) and `--scrim` (the shade under a dialog, a drawer or the login photo). `--status-fg` is not `--action-primary-fg`: that one stays white over the accent by decision, this one follows contrast. **Small status text (below 18px, 14px if bold) must reach 4.5:1 on its real background, in every state and all sixteen combinations; straight `--danger`/`--success` only does so on `--surface`**: pure `--success` is 3.2:1 on a light surface and several plain `--danger` texts measured 4.0–4.3:1 on their own real background (`--folders-bg`, `--surface-sunken`, a hovered or selected list row). Anywhere else — a tinted fill, `--folders-bg`, `--surface-sunken`, a list row — the element sets a local `--status-tone` and joins the one shared rule (`.alert-error, .toast-success, .toast-error, .svc-account-pill.is-ok/.is-fail, .svc-account-test-result.is-ok/.is-fail, .contact-scopes-error, .calendar-sidebar-error, .message-row-draft, .message-row-priority.is-high, .contact-editor-photo-error, .compose-attachment-error, .invitation-card-badge.is-cancel, .invitation-card-error, .invitation-card .btn-danger, .recipient-token.is-invalid, .row-tag.is-warn` — grep for the full list) that mixes the tone 55% with `--text`, measured to clear 4.5:1 on every background and state (resting, hover, selected) it is actually drawn on, in all sixteen combinations. A border or an opaque status fill (a filled `.btn-danger:hover`, a pill's own boundary) is not text and keeps the straight colour, since it only needs 3:1 and reads it easily.

Mail added role tokens across all four palette-mode blocks, for states a settings pane does not have: `--list-row-hover`, `--list-row-selected-bg`/`-fg`, `--list-separator`, `--badge-count-bg`/`-fg`, `--reader-header-border`, `--quote-text`. `--accent-unread` was provisioned in the shell slice and has consumers only since the mail module. `--attachment-chip-bg` went the way of `--list-row-unread-bg` when the reader's chips took the accent fill.

**`--action-primary-fg` is `#ffffff` in all sixteen blocks, and that is a decision rather than an oversight.** It was per-mode — near-black over dark mode's light accents, which reads better on a contrast meter — and was rejected on look: the owner wants white text over the accent in both modes. Every consumer sits on `--action-primary` (`.btn-primary`, `.btn-add`, the blocked-images button and its seam, the attachment chips, the identity pill, the rule wizard's step circles, the alphabet index's hovered letter, and the toggle knob, which rides the accent when on and a grey track when off), so the token stays the one place to change it, and no component hard-codes a white. Do not "restore" the per-mode values, and do not collapse the token into a literal. **Unread rows deliberately wear the selected tokens** (background, fg, inset bar) plus bold and the dot — same tokens rather than copied values, so the two looks cannot drift apart; the old `--list-row-unread-bg` was removed with its last consumer. What still singles out unread among selected-looking rows is the bold and the dot.

Palette and theme are selected via `data-palette` / `data-theme` attributes on `<html>`, persisted in `localStorage` (`appearance_palette`, `appearance_theme`; theme is `'light' | 'dark' | 'system'`). A blocking inline `<script>` in `index.html` reads both keys and sets the attributes **before first paint** (avoids a flash of the wrong theme) — it duplicates the resolution logic that `ThemeContext` also runs, deliberately, since the context only mounts after React hydrates. **It therefore also repeats the palette names**, which it cannot import — `PALETTE_IDS` (`ThemeContext.tsx`) is the module-side list, and `palettes.test.ts` asserts the two agree. Forgetting the script half produces a bug no other test sees and no reviewer notices: on reload the script rejects the stored palette, paints `night`, and React corrects it a frame later — a flash, on first load, for one palette.

`ThemeContext` (`src/contexts/ThemeContext.tsx`) owns `theme`/`palette` state, re-applies the `data-theme`/`data-palette` attributes on change, and (when `theme === 'system'`) subscribes to `matchMedia('(prefers-color-scheme: dark)')` for live OS-theme changes. `AppearancePage` is the only UI that calls `setTheme`/`setPalette`.

**Night `--action-primary` hue-shift** — deliberate: in the night palette, `--action-primary` is navy in light mode but shifts to coral in dark mode (`theme-night.css`, see the comment above the dark-mode block) because navy would dissolve into the dark background. The *role* (`--action-primary`) is stable across modes; the *hue* backing it is not. Do not "fix" this into a single fixed color. `forest` and `plum` do the same for the same reason — evergreen and aubergine both dissolve into a dark ground, so dark mode promotes their amber and gold to `--action-primary`.
